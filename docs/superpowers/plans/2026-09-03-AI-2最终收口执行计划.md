## 5. 阶段 B：把发布门禁接入真实路径

### B1. 统一 B3 证据字段

在 `backend/app/release_gate.py` 中定义唯一的 B3 证据输入，至少包含：

- `run_id`、`environment`、`external_live`；
- `provider`、`model_id`、`source_commit`、`deployment_commit`；
- `manifest_sha256`、`result_sha256`、结果状态和完整分析状态；
- 三个 Agent 的完成状态、真实 provider call 数量及可追踪 call ID；
- 事后事实闸门结果、是否 superseded；
- 真人评分完成状态和评分记录 ID。

缺字段、类型不对或状态不明确时，统一返回 `false + reason_code`。

### B2. 收紧 `evaluate_b3_eligibility`

现有实现只检查部分字段长度和前缀，需要补上：

1. `run_id` 必须匹配实际运行记录，不能接受任意 `RUN-xxx` 字符串。
2. commit 必须是完整十六进制 SHA-1，并与冻结的源代码/部署 HEAD 核对。
3. result 和 manifest 哈希必须是完整十六进制 SHA-256；有文件时重新计算，不能只看长度。
4. `external_live=true`、环境为 production、provider 身份与当前目标一致。
5. 结果必须达到项目规定的完整终态；不能用裸 `model_success`、缓存、回放或 deterministic backup 代替。
6. 三个 Agent、三次真实供应商调用、事后事实校验和真人评分必须全部存在证据。
7. superseded run 永久拒绝进入正式 B3。

### B3. 收紧 `evaluate_release_ready`

发布门禁至少要核对：

- 工作区 clean；
- 当前 HEAD = `materialized_source_head` = release evidence head = deployment commit；
- manifest 实际哈希与发布记录一致；
- current evaluation 与 release evaluation 的 ID、模型和 raw record 状态一致；
- current evaluation 不得是 `initialized_no_model_runs`；
- signoff 已针对当前受签文件重新生成且状态 approved；
- fresh B3 证据通过 `evaluate_b3_eligibility`；
- 人工评分完成；
- 真人最终发布批准存在且绑定当前快照。

### B4. 接入 `/api/status` 和控制脚本

- `backend/app/main.py` 的 release readiness 改为调用生产门禁函数。
- `state.release_readiness.fresh_production_b3_completed` 只能作为被核验的历史输入，不能直接打开门禁。
- `scripts/run_controlled_b1_b3_prescore.py` 使用同一套函数，禁止脚本和 API 各自维护一套规则。
- API 返回可读的 `ready_checks`、`blocked_reason_codes` 和证据 ID，不返回内部路径、密钥或历史调试数据。

### B5. 补契约测试

在 `backend/tests/test_release_gate_contracts.py` 增加正反用例：

- 任意一个 B3 字段缺失；
- 假 run ID、假 commit、非十六进制哈希；
- deployment/source/materialized HEAD 不一致；
- provider probe 通过但没有真实业务调用；
- fallback/cache/replay 伪装成 B3；
- raw records 未初始化；
- signoff stale；
- 没有最终批准；
- 所有证据齐全时才返回 true。

另在 API 测试中证明：即使写入 `fresh_production_b3_completed=true`，没有真实证据时 `/api/status` 仍然返回 false。

验收：所有门禁规则只在生产模块定义一次；测试能证明 API 和控制脚本确实使用该模块；选择性测试通过且无网络、无付费模型调用。

| 人工评分 | B0–B3 评分表 | 当前 evaluation 完成，评分可追溯 |
| 最终批准 | 真人批准记录 | 明确绑定当前发布快照 |

## 11. 执行顺序与停止规则

执行顺序固定为：

1. 阶段 A 事实快照；
2. 阶段 B 门禁生产化和测试；
3. 阶段 C 清洁环境预验收；
4. 阶段 D 报告口径修正；
5. 阶段 E 重建唯一评委包；
6. 真人确认冻结、提交和部署；
7. 阶段 F 新鲜 B3、重新签字、人工评分、最终批准；
8. 最终矩阵复核并更新 `competition_release_ready`。

遇到以下情况立即停在当前阶段：

- 清洁环境仍引用仓库 venv；
- 历史根因没有逐项日志；
- 当前 HEAD 与发布快照不一致；
- 测试出现未解释的间歇性失败；
- provider 只有 probe，没有真实业务调用；
- 使用 fallback/cache/replay 代替 B3；
- 人工签字或最终批准缺失。

停止时保留失败日志，报告“卡在哪个门”，不通过改数字、删除失败记录或放宽判据继续前进。

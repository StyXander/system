# AI-2：评委复现与发布门禁可靠性计划

> 计划日期：2026-09-03  
> 负责人：AI-2（后端、测试、打包和发布证据）  
> 任务类型：工程可靠性与发布候选整改  
> 当前状态：待执行

## 1. 目标

把“源码仓库能跑”“评委包能跑”“当前发布候选可追溯”“生产模型真的可用”四件事分开测量，再把它们按同一版本绑定。最终要能回答：

1. 评委拿到什么文件；
2. 在没有密钥和受限年报全文时，哪些测试会运行、哪些会明确跳过；
3. 当前代码、评估记录和部署版本是不是同一份；
4. 生产真实模型是否验收，若没有，系统如何诚实降级。

## 3. 执行顺序

### Phase 0：基线与事实冲突登记

执行只读校验：

```powershell
backend\.venv\Scripts\python.exe -c "import json;json.load(open('PROJECT_STATUS.json',encoding='utf-8'));print('JSON_OK')"
git check-ignore -v docs/TEST_INVENTORY.md scripts/test_inventory.py scripts/build_delivery_packages.py scripts/axe_inject.py scripts/browser_demo_final_acceptance.py
git status --short --branch
git rev-parse HEAD
```

登记：当前 HEAD、工作区 dirty 状态、发布记录绑定的源头、评估模型、dashboard 哈希、manifest 哈希和部署状态。`git check-ignore` 无输出且退出码为 1 才表示这些文件未被忽略。

输出：`tmp/reliability-baseline-20260903.md`。发现冲突时先列事实，不直接改历史记录。

### Phase 1：拿到评委包 19 个失败的真实名单

修正或重写 `scripts/diagnose_judge_package.py`，确保 Windows 输出使用 UTF-8，不因中文路径或错误字符中止。诊断过程必须：

1. 物化评委包源码和生成文件；
2. 删除全部模型密钥与 `.env`；
3. 不带完整年报全文运行；
4. 保存完整 pytest 输出；
5. 逐项记录 `FAILED`、`ERROR`、`SKIPPED` 的真实名称和原因。

输出：`tmp/judge-failures-20260903.md`。19 项必须分成“需要受限年报全文”“仓库专属”“真缺陷”三类，真缺陷不能靠 skip 处理。

### Phase 2：建立测试分层和全文依赖闸门

对确实需要标准股份年报全文、来源哈希或 RAG 索引的测试增加显式 marker，例如 `requires_full_corpus`；只在全文缺失时跳过，并打印清楚的补齐方式。仓库专属测试标记为 `repository_only`，不进入评委包。

新增契约测试，至少证明：

- 无全文时依赖用例是明确跳过，不是失败；
- 有全文时该用例会运行；
- 本机源码仓库若声明有全文，不得静默跳过；
- 真缺陷仍然失败。

如需下载和哈希校验全文，先写 `scripts/prepare_full_corpus.py` 和离线校验测试；联网下载步骤保持待真人授权，不把下载成功当成来源合规通过。

### Phase 3：让评委包可独立构建与复验

改造打包脚本，使其支持独立构建某一个包、只校验和指定输出目录。评委包至少包含：

- 源码和必要测试；
- `requirements.txt`、必要的开发依赖说明和启动 README；
- `.env.example`；
- 脱敏 Demo 或明确的离线运行模式；
- 测试清单和已知边界；
- 不含密钥、`.env`、个人签字、未授权全文、本机绝对路径和仓库临时缓存。

在新临时目录中验证：

```powershell
backend\.venv\Scripts\python.exe -u scripts/diagnose_judge_package.py
```

如果计划要求新建虚拟环境，必须分别记录依赖安装、测试运行和失败原因，不能只复用当前解释器后宣称“干净环境通过”。

验收目标：评委包 `0 failed`；受限全文依赖项只能是明确 skipped；跳过数、运行数和测试清单一致。

### Phase 4：当前版本与发布门禁绑定

检查并补充反向测试：

- 工作区 dirty 或 HEAD 与发布证据源不一致时，`competition_release_ready` 必须保持 false；
- `deployment_commit`、接受的源码 HEAD、manifest 和评估记录必须能互相核对；
- `current_evaluation` 的模型 ID、raw records、dashboard 和运行证据必须一致；旧模型记录只能保留在历史或 superseded 区域；
- R1 受签文件任一变化后，签字状态必须回到 `stale_requires_reapproval`；
- 新鲜 B3 不能只依赖一个可手改的布尔值，必须绑定 run_id、环境、模型、commit、调用数和结果哈希；
- 缺少最终真人批准时，即使其他条件满足，发布仍为 false。

不得修改旧原始评估记录来消除模型冲突；需要新评估时追加新记录并重新生成派生 dashboard。

### Phase 5：旁路观察器与内部接口安全

按已有实施计划检查两项：

1. 旁路观察器失败是否进入可持久化的 `result.context`，并在刷新后仍能看到“留痕通道降级，主分析未受影响”；
2. `/api/internal/status` 是否默认拒绝外部请求，回环信任是否需要显式本机开关，反向代理信任网段是否精确配置。

新增正反测试，确认安全修复不会把本机调试误判为生产可用，也不会放宽公开状态接口。

### Phase 6：清洁 Git 快照复算

只有在前述代码和测试修改完成、且真人明确授权提交后，才允许从 Git 快照执行：

1. `git archive` 导出；
2. 新建虚拟环境安装依赖；
3. 运行测试和启动 smoke；
4. 检查无 `.env`、无密钥、无私人全文；
5. 检查页面和 15 案例入口能实际打开。

本阶段计划本身不执行 `git commit`、`git push` 或部署。

## 4. 验收矩阵

| 门 | 通过条件 | 不得替代的证据 |
|---|---|---|
| 评委包 | 干净解压无未解释失败，依赖全文项显式跳过 | 源码仓库本地全绿 |
| 环境复现 | 新环境能安装并执行 README 命令 | 当前解释器一次运行 |
| 版本绑定 | HEAD、manifest、评估、部署提交一致 | `git push` 成功 |
| 模型链 | 真实环境、真实 run、真实调用和三角色状态齐全 | configured、probe、缓存、备用链 |
| 签字 | 当前受签文件哈希一致且真人重新批准 | 历史签字原件 |
| 安全 | 公开接口拒绝未授权访问，失败留痕不改写主链 | 静态代码扫描 |

## 5. 交接与停机条件

交给 AI-1：可公开读取的结果字段、错误状态和证据定位缺口。  
交给 AI-3：最终测试数字、包边界、版本号、模型状态和可以写入材料的证据路径。  
交给真人：生产 provider probe、单案例付费 B3、签字、人工评分和发布批准。

遇到以下情况停止并报告：测试失败原因还未测量、需要覆盖历史记录、需要密钥、需要下载受限材料、需要部署或需要把 pending 改成 passed。

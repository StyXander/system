# AuditTrace 概览复核与审查、修改计划

日期：2026-09-07。对象：数智竞赛目录中的当前 AuditTrace；任务类型：工程及竞赛交付概览复核。

AI生成内容，仅供审计计划阶段进一步核查，不构成审计结论或审计意见。

初版范围曾限定为只增加计划和抽查证据，不修改业务代码、正式方案书、发布指针或人工记录。用户随后要求“按照审查结论重新制定计划并修改”，因此本文件第七节为当前执行口径：允许修复已复现的低风险工程缺陷，仍不改正式发布指针、人工记录，不提交、不部署、不调用付费模型。本计划不等同于全量验收。

## 一、总体判断

项目已经具备较完整的工程控制，继续重复正常路径自测的收益有限。2026-09-04 的最终整合报告已有本地浏览器、安全、导出与清洁包证据；本轮没有重新执行这些完整流程，不能把历史通过改记为当前通过。

现在最需要解决的是三件事：校验器是否真的核对底层证据；发布流程是否既能拒绝错误状态，也能让合法候选闭合；三 Agent 相对简单方法的业务增益是否有公平、独立的评价。暂不建议扩展新规则、新 Agent 或大规模改版。

检查开始时 HEAD 为 `26059cfc79643f05b37d706393ebbb851dc32f80`，Git 工作区未报告改动（存在全局 ignore 文件读取警告）。本轮新增审查文件后自然会出现未提交文件，不能据此说原工作区不干净。

## 三、下一轮审查计划

### A0：冻结审查对象，建立覆盖矩阵（约 0.5 天）

1. 记录源码 HEAD、工作区差异、manifest 规范化哈希、规则/提示词/模型配置指纹、测试清单和交付包哈希。秘密不进入快照。
2. 将已有 9 月 4 日记录标为“历史已执行”，逐项判断当前改动是否影响它。只重跑受影响项及关键端到端流程。
3. 建立 `需求 → 路由/函数 → 测试 → 原始证据 → 环境/版本 → 结论` 表。没有原始证据的通过声明标为待复验。
4. 清楚分离源码环境、无全文评委包、补齐全文后的包、本地真实模型、生产环境五种范围。

产物：唯一基线清单、测试映射表、问题台账。验收：每个后续结论都有版本、环境、证据和责任人；不以测试总数替代覆盖说明。

### A1：对发布和 B3 门禁做反例审查（约 0.5—1 天，优先）

1. 先把 F01 的四个最小复现纳入可重复检查，覆盖缺角色、错误角色、额外角色、重复/空调用编号、空/不存在评分编号。
2. 追踪 `main.py → 证据文件 → run_store/台账 → provider 调用 → 人工评分`；分别篡改 run_id、模型、案例、结果字节、manifest、提交、角色和评分关联，必须拒绝或明确待核验。
3. 测试同一调用 ID 出现在不同角色、不同 run 借用同一结果、旧签字移植到新规则、字符串 `"false"` 被转成真值的情况。当前 `main.py` 对最终批准使用 `bool(...)`，需要在真实入口核验严格布尔类型和记录来源。
4. 验证时间新鲜度：旧但同版本的运行是否还有效、生产证据是否确属生产、过期 probe 是否失效；预先确定有效期，不能测试后随意改阈值。
5. 在临时隔离仓库完整走一遍合法候选流程，检验 F03 是否出现“写入 HEAD → 提交 → HEAD 又变化”的循环。

验收：错误证据逐项被拒绝且有原因码；合法证据在隔离测试中可完成门禁。模拟人工批准只用于隔离测试，绝不回写正式记录。产物：正反例结果、证据加载链图和版本绑定设计结论。

### A2：专业数字与证据审查（约 1 天）

1. 从已冻结案例中预先选六类：R1 触发、不触发、资料不足、跨期变号、行业差异、修订年报。尽量覆盖不同企业，记录选择理由。
2. 对每案人工核对公司、年度、合并/母公司范围、元/万元、净额/余额、修订版、PDF 页序与印刷页码；独立复算增速、差值及舍入。
3. 沿一条实际结果检查 `原文 → 字段 → 程序数值 → claim → 反证 → 复核 → 导出`，不能只验证 evidence_id 存在。
4. 注入晚于 T0 的资料、其他案例片段、过期 RAG 快照和“忽略之前指令”式文档内容，检查证据隔离与提示注入边界。
5. 请真实专业复核人检查正常解释是否有依据、资料清单是否可执行、未触发结果是否误导为无风险。AI 可以整理核对表，不能代作专业签字。

验收：选中关键金额和公式全部能复算；跨案例/T0 泄漏为零；每条结论支持类型正确；缺口如实呈现。资料不足只标未通过或待核验，不补造字段。

### A3：故障与状态恢复审查（约 1 天）

基于现有任务竞争和 fencing 测试扩展组合，不另建第二套状态机。核心矩阵：本地/公开环境 × 正常/超时/取消/中断/重试/配额拒绝/持久层故障 × 刷新/双标签/跨用户。优先覆盖高风险组合，不机械跑所有笛卡尔积。

重点步骤：双击启动；两个页面同时提交；一个页面取消另一个刷新；模型返回前取消；数据库写入失败；执行实例重启；旧 worker 延迟回写；任务 TTL 到期后读取；缓存命中与真实调用并发。数据库故障注入使用隔离测试库。

验收：完成状态不被旧回写覆盖；取消/中断不显示成功；无跨用户泄漏；无意外重复业务调用；已发生 HTTP 尝试按事实计数；重试创建/关联规则明确。只测试本地替身不能宣称 Supabase 实测通过。

### A4：评委首次使用与交付审查（约 0.5—1 天）

1. 四个既定视口运行真实页面和后端，检查首次进入、选择案例、启动、等待、失败恢复、证据回查、下载、打印；保留控制台/网络/截图证据并查看截图。
2. 检查所有关键状态的键盘、焦点归还、触控、读屏名称与非颜色提示。既有 axe 结果只能覆盖当时已测状态。
3. 请两位未参与开发的人独立完成“找到一个待核查事项、指出原文依据、说明下一步”；记录时间、错误和求助次数。30 秒挑战作为观察指标，是否必须 30 秒由演示目标预先决定。
4. 对同一 run 的页面、JSON、CSV、DOCX/PDF核对数值、计算过程、来源、状态和统一声明；真实导出与渲染核对后才能通过。
5. 独立解压评委包，默认无全文执行一次，再按已有脚本补齐授权范围内的全文执行一次；逐项解释 373 与 346+19 的历史差额，并用本次收集清单替代旧数字。

验收：代表任务无需开发者解释即可完成；下载与页面同源同 run；包内无秘密和非预期资料；所有排除/跳过项可追踪。交付包缺全文的限制不应被包装成完整分析通过。

### A5：三 Agent 效果评价（准备约 0.5 天；运行与真人评分另计）

保持既定 B0/B1/B2/B3 定义。先由真人冻结案例、T0、模型、合同、预算、指标与评分表，再开始正式评价。B2/B3 优先共享相同事实输入和可比较的输出任务，同时保留各自方法特点。

至少分开报告：Schema 合格率、事实与引用正确性、有效待核查事项、正常解释质量、人工修正量、耗时、成本、首过率、最终完成率和失败原因。不能通过排除失败样本改善结果。建议两名真实评分者盲评并记录分歧；若只能一人，明确这一限制。

15 个冻结案例可作工程覆盖集合，不自动成为足够的统计样本。需要论证增益时，再由专业人员确定样本规模与成功标准；相同模型多跑几次只说明重复稳定性。若 B2 主要失败于合同，先修公平性问题，不能把这类失败直接当成三 Agent 的业务优势。

验收：原始记录可追踪、失败样本保留、真人分数真实；结果不支持优势时如实报告。生产付费跑批和正式冻结遵循既有授权与真人决策边界，本计划本身不启动这些操作。

## 五、停止条件和报告规范

每条问题只保留一个编号，记录复现步骤、预期/实际、影响范围、根因、修改文件、反例回归和证据路径。历史已修项只补回归，不反复重新立项。

审查完成需满足：P1 已关闭或有真人明确接受的限制；所有待执行项明示未执行；关键正反路径在同一候选版本成立；交付包与当前材料可对应。正式发布另需实际生产证据、专业签字、真人评分和最终批准，不能由审查报告代替。

如果出现新的高风险失败，暂停相关发布动作并缩小复现，不用反复全量重跑掩盖根因。若本轮复核没有发现新失败，不再重复检查不受影响的历史项目。

# AuditTrace 挑战杯改造与验证方案

本方案按任务及验收条件组织，不按日期分配。审查基线为 GitHub main 的 c99edae，修复提交另见 BUGFIX_ACCEPTANCE.md。本文区分已经实现的功能、实际运行记录和仍需取得的效果证据。

## 一、先确定目前能交代到哪一步

建议继续以科技发明制作 B 类准备，软件作品的受理口径沿用指导老师已经确认的意见。最终类别、组别、提交字段和资格，以学校正式通知及申报系统为准。团队人数和成员学历须按真实名单核对，不能仅凭历史对话填写。

现阶段更准确的定位是：面向财务与 ESG 编制、复核及鉴证准备人员，围绕一个可持续事项，关联公开年报与可持续发展报告中的证据，区分已披露事实、候选财务机制和缺失资料，并导出供人工复核的事项档案。公开披露关联不能证明企业内部实际入账，也不能据此出具审计或鉴证意见。

| 当前材料 | 已经能说明什么 | 还不能说明什么 |
|---|---|---|
| 可运行网站、代码、导出功能 | 软件制作和部分工作流程已实现 | 专业结论正确、性能优于通用模型 |
| 宝钢、五粮液、美的的登记报告和运行记录 | 已接触真实企业披露，能定位部分原文；部分任务真实调用过模型 | 三家企业均已稳定完成、已经通过独立业务验收 |
| 宝钢多组调用回执 | 能记录模型、预算、失败和固定证据 | 五 Agent 必然优于单模型；不同修复版本可合并统计 |
| 六个开发问题、标注规程 | 有人工标注的准备材料 | 已有人工金标、已有独立测试集 |
| 试用表、技术交底、软著源码材料 | 可以支持后续真实办理 | 已经试用、已申请、已受理或已获得知识产权 |

用户提出的三个重点——真实企业完整验证、人工比较、实用性——目前都没有形成可以支撑竞争力结论的完整证据。这些工作应优先于继续扩展页面、增加 Agent 数量或堆材料篇幅。

## 二、按学校实际评分标准准备证据

依据用户提供的《北京工商大学“科创杯”大学生课外学术科技作品竞赛评审标准参考》附件第 3 页，科技发明 A、B 类采用下表权重。附件没有给出“发明专利＞实用新型＞受理”的排序，也没有把专利列为参赛必备资格。

| 评分项 | 附件关注点 | 当前主要缺口 | 要形成的证据 |
|---|---|---|---|
| 科学性 30% | 方案合理、技术操作可行、性能优良、与同类作品相比有优势 | 工作流仍有部分失败；题目与指标尚未完全对应；缺独立人工答案 | 真实企业逐项验收、完整运行率、独立标注、同条件比较、引用复核与错误分析 |
| 先进性 30% | 构思、制作方法、关键技术、主要指标的独特之处，与现有技术相比的实质进步 | “五 Agent＋规则”本身不足以证明先进；宝钢有专项处理，泛化尚未证实 | 现有方法对照、模块消融、未参与调试企业的测试；给出效果与成本的取舍 |
| 现实意义 40% | 效益、成熟程度、影响，荣誉认证传播及专利软著，社会效益 | 缺真实参与者使用记录；没有可靠工时节省和采用情况 | 人工独立完成与系统辅助的比较、实际试用任务、修改记录、采用反馈、真实知识产权办理材料 |

这里的样本数、测试阈值和材料清单均为项目建议，除明确引用通知的内容外，不是学校额外规定。不能用“准备了材料数量”代替“证明了作品效果”。

## 三、先完成的产品与技术改造

### T1. 把具体问题作为运行输入保存

每条任务必须绑定 `case_id、question_id、question、research_task_type、report_set_id、matter_id、as_of_date`，并记录报告哈希。模型实际看到的问题、人工任务单的问题、最终评分的问题必须逐字对应。

本轮已补后端问题字段、模型上下文传递、运行版本记录及实验脚本的清单校验。后续在工作台增加“本次要核对的问题”和相应结果标题；历史恢复与 Word/CSV 导出也要展示该问题。验收时用同一事项的两个不同问题分别运行，检查历史、结果和导出没有串题。旧记录没有问题身份，保留为调试记录，不反向补写为正式实验。

### T2. 分开评价“关系成立”与“金额一致”

这是目前最需要补的专业逻辑。不能把“有证据表明项目与在建工程有关”转换为“ESG 金额与年报金额一致”。建议保留两套输出：

| 任务 | 应回答的问题 | 建议标注与评价 |
|---|---|---|
| 关系追踪 | 是否有直接披露支持事项与具体财务项目的关联，哪些链条仍属推测 | 直接支持、部分支持、存在反证、证据不足；逐段评价证据，不硬套金额一致性 |
| 金额核对 | 同一主体、期间、范围、定义、单位及计量基础下，两组金额能否核对 | 确认一致、疑似冲突、已解释差异、不可比、证据不足；只有满足明确条件才可确证 |

当前生产 `MatterAssessment` 没有 `numeric_consistency`，条件试算也明确 `formal=False`。本轮保留这条限制，并在评测报告中明示，未通过增加模型自填字段解决。完整改造须增加程序生成的金额核验记录，至少包含：

- 左右比较对象、原始金额定位 ID、报告页码、金额单位与精度；
- 主体、期间、项目身份、覆盖范围、计量基础和去重依据；
- 期初＋本期增加－转固－其他减少＝期末等具体等式，采用哪些项及符号；
- 调节项是否为报告明示，还是尚待验证的解释；破折号、空格和未披露值保持未知；
- 用 Decimal 复算的原值、差额、依据原文精度预先确定的容差；
- 每项条件的证据与复核状态、程序规则版本。身份和语义仍未确认时，输出条件试算。

模型只能提出核对计划，不能自行把状态写成“程序已确认”。专业人员确认的语义前提应另记复核记录，保留自动结果。验收必须同时包含能确认的正例、近似金额但口径不同的反例、存在明确调节项的案例、缺必要数据的案例。若真实报告找不到正例，就缩小金额核对的主张；不能用伪造企业数据补正例。

### T3. 将宝钢专项能力改造成通用表格取证

当前存在企业编码、固定页码及专项解释。宝钢可以作为明确标注的示范适配，不能单靠它证明通用能力。改造为：按项目名称与附注标题找候选页，识别表头、单位和跨页延续，定位目标行，保留单元格与页面证据。候选行名称近似时，要求来源支持身份关系。

把企业专用别名、固定页和解释放入显式配置；正式测试时声明配置是否允许，禁止在看过测试答案后继续为该企业补规则并沿用原测试结果。对至少两家未参与调试的企业，在不增加企业专用代码的条件下跑同类任务。记录抽取失败和不适配原因，不用只展示成功截图。

### T4. 修复真实任务的剩余失败

按失败回执分别处理 HTTP 供应商故障、结构校验、工具轮次耗尽、来源读取失败和实例中断。供应商故障与业务证据不足分开。对结构问题保留有界反馈修正；对检索问题检查查询与检索命中，不能一律提高调用上限。

本轮已修正评测完成判定、未知用量、备用模型配置识别、重试条件校验；Render 批量脚本遇到供应商故障会停止继续启动更多组。后续补轮询 GET 的有界重试与部署重启后的任务恢复验收，POST 不得因网络含糊重放新付费任务。

建议工程验收线：选定的开发任务都能取得终态、历史和导出可恢复，失败原因可追溯，任何失败均不会显示为业务已通过。正式测试仍须报告全部任务的完成率。这里的工程验收线不代表准确率指标已经达标。

## 四、真实企业运行验证：具体要做什么

### V1. 建立开发集与独立测试集

现有六个问题继续作为开发集。先逐一确认事项编号仍有效，问题可由现有公开材料回答到什么程度，材料覆盖是否足够。宝钢第 154 页的金额提取不自动构成整个零碳工厂的投入勾稽；五粮液环保投入不自动构成资本支出；美的气候风险叙述不自动证明进入减值估计。这些均是待核查命题，不预填企业有错或无错。

独立集建议从 4—6 家企业中选择约 16—24 个问题，至少两家未参与提示词、规则及专项适配调试。尽量覆盖制造业与其他适配行业，并纳入能完成关联的正例、范围或期间错配、缺证、明确解释差异、跨期承诺等情况。数量只用于控制本科团队工作量；不足以自动支持行业普遍结论。

先按研究问题筛选材料，再由独立人员标注，不按系统表现挑选案例。公开报告没有真实冲突时，不强凑“发现企业造假”案例。人为修改金额、交换主体的压力样本单独登记为合成测试，不计入真实企业准确率。

### V2. 为每个问题制作可复核任务包

每包包含任务清单、来源链接、报告下载时间和哈希、截止可用日期、原始 PDF 页码与印刷页码的对应方式、允许的资料、统一提交表。固定证据实验给所有条件同一份证据；端到端实验给同一资料集合，允许各条件按协议检索。

输入包不得含标准答案、预期标签、脚本内部提示答案或隐藏的企业专用结论。专项结构化表格属于额外输入，必须纳入输入哈希；本轮已经补齐这项记录。公开仓库不提交不必要的报告全文或参与者个人信息。

### V3. 实际完成每家企业的端到端验收

按“选择资料→选择事项和问题→真实模型运行→原文复核→处理证据缺口→导出→重新打开历史”完成一遍。每个任务记录代码提交、供应商响应型号、配置、预算、全部角色终态、调用回执、耗时、实际 Token 及未知项、导出结果。

保存成功和失败的原始 JSON。检查引用能否打开正确报告与页面、引文是否存在、引文是否支持本次具体结论。SHA-256 只能证明文件身份与字节完整性，不能证明会计解释正确。运行结束、模型请求成功和专业结论正确分别统计。

交付物为一份逐企业验收表及其原始记录索引。三份重新排版的 Word 底稿，不能替代这一步。

## 五、专业答案与模型比较

### E1. 取得独立人工答案

建议找两位具备相应会计或审计知识的人员分别作答，有条件再由老师或实务人员仲裁。登记匿名编号、角色和经验，不把同一人换两个编号当作独立标注。标注者先看任务与报告，不先看系统答案；开发者提供资料和操作帮助时，记录介入情况。

每题提交标签、原文证据、判断理由、无法确认之处及下一步资料。分歧保留，仲裁另记原因。计算原始一致率与适用于名义标签的未加权 Cohen's kappa，并列出分歧类别；所有人都只使用一个标签时，kappa 可能无法定义，不能写成 1。关系类与金额类分开标注，不能共用含义不清的答案。

金标参与者与可用性实验参与者可以部分重合，但不能让已经背过同一道题答案的人再承担该题的计时任务；开发者不适合作为证明产品省时的唯一用户。

### E2. 先跑四组同条件比较

| 组别 | 架构 | 会计门禁 | 要检验的作用 |
|---|---|---|---|
| G1 | 单模型工作流 | 关闭 | 同接口模型基线 |
| G7 | 单模型工作流 | 开启 | 门禁在单模型中的增益和损失 |
| G6 | 五角色工作流 | 关闭 | 多角色分工在无门禁条件下的作用 |
| G3 | 五角色工作流 | 开启 | 完整方案的质量、完成率与成本 |

这里的 G1 仍包含项目的建档、结构化接口和来源约束，不应称为“普通用户直接上传到 ChatGPT”。若要回答评委的直接问答问题，再加一个明确记录提示词、模型、材料和输出格式的直接问答基线，避免偷换比较对象。

固定模型及响应型号、温度、资料、题目、截止日期、工具权限、输出要求、反馈修正机会及总预算上限。记录实际调用和 Token，不宣称“调用次数相同”。相同调用上限不等于相同实际计算量；增加一张质量—成本表，有条件再做同成本预算比较。固定证据与端到端分两轮，不把两种模式的结果混算。每条件建议重复三次，组别次序轮换；重复运行不是增加独立企业样本数。

先验收一个完整四组小批次，确认题号、输入哈希、版本、输出和标注均对应，再扩大。若同轮发生部署更新或供应商切换，该轮标为不可直接比较，重新组织运行；不要将不同修复版本凑成一张“最佳成绩”表。

### E3. 同时报告质量、覆盖与失败

| 指标 | 分母及含义 | 报告限制 |
|---|---|---|
| 完成率 | 技术上合格完成的任务数／全部启动任务数 | 已保存 JSON 不等于合格完成；预先声明的角色消融单列 |
| 结论正确率、分类 F1 | 有人工答案且技术完成的任务 | 同时报告对应样本数和类别分布；任务类型分开 |
| 端到端正确交付率 | 正确且完成的任务／全部有金标的启动任务 | 技术失败保留在分母，防止只展示成功样本 |
| 错误确证率 FCR | 错误确证数／全部确证数 | 没有确证时为 N/A，不能写“错误率 0” |
| 确证覆盖与召回 | 确证数／总题数；正确确证数／应确证题数 | 防止全拒答看似安全；当前金额确证能力尚待完成 |
| 引用正确与证据支持 | 能打开原页、引文存在、确实支持判断分别统计 | 不同系统的随机 evidence_id 不能直接当语义匹配；映射至报告哈希、页和片段 |
| 耗时及资源 | 包含失败的整体耗时分布，实际调用、已知 Token 与未知数 | 不把预算上界当实耗，不估造费用或人工成本 |

结果给出逐题表、混淆矩阵、按企业/任务类型的分层结果和典型错误。重复结果报告波动；置信区间按企业或独立案例聚合，不能把同一案例的重复调用当独立样本。小规模样本用于初步验证，不给夸张的显著性或推广结论。

### E4. 再做有针对性的消融

A4 消融只用真正存在竞争性解释、反证和缺口的题，检查增加了哪些有效反证，以及是否引入多余怀疑和耗时。A3 消融用有多期原件的承诺追踪题，检查承诺、报告期、发生期是否区分。每次只改变声明的组件，其他条件固定。若没有明显增益，缩小创新主张或改进组件，不用只报告最有利案例。

## 六、跟人工对比与实用性：两项研究都要做

### H1. 比较人工独立完成与系统辅助完成

目标是比较产出达到相同质量要求时的总工作时间。系统生成耗时不能直接与人工完整核查时间比较。建议采用小规模交叉试验，招募约 4—6 名具备基础知识的参与者，尽量含真实目标用户；若只能招募同学，明确定位为学生试用，不代称事务所采用。

先用单独的练习题熟悉软件和提交要求。把正式题分成难度近似、资料量近似但答案不同的 A/B 两套。部分参与者先人工做 A、再辅助做 B；另一部分反向安排。不要让同一个人先手工作答某题后，再用软件做同题比较时间，记忆会使第二次天然占优。

人工条件允许 PDF 搜索、Excel 和统一计算工具；辅助条件增加 AuditTrace，其他资料范围一致。两种条件都须提交相同结构的结论、引用、口径判断、未决事项和下一步资料清单。明确禁止或允许的其他 AI 工具，并一致执行。

从打开任务单开始计时，到提交达到预定要求的底稿结束。辅助条件计入等待、原文回查、纠错、导出和复核；保留失败任务和超时。独立评阅者尽量不知道底稿来自哪个条件，按同一规则检查质量。先比较正确交付率与重大错误，再比较时间，不用质量下降换取“提速”。

交付 `human_study_sessions.csv`、匿名任务底稿、原始计时依据及评分记录。报告每人的配对结果、中位耗时和范围、纠错时间、失败与弃用情况。题目只做到了难度匹配时，说明限制；无可比的配对结果不强做精确提升百分比。

### H2. 完成真实工作任务试用

先访谈目标用户，确认他们当前如何核对、用哪些工具、最终交付什么。随后请老师课题组、企业财务/ESG 人员或事务所人员选择一项真实可用的任务使用系统。公开报告复核就是公开报告复核，不写成已接入企业内部账簿或实际审计项目。

记录用户采用了哪些结论、修改了哪些内容、哪些输出仍需重做，系统多提供了哪一条可复核证据，以及最终是否进入其工作材料。问题清单至少覆盖：检索是否省事、缺证提示是否具体、引用是否可靠、导出是否可用、等待是否能接受、下次是否愿意使用及原因。

如果用户发现系统不适合流程，也保留反馈并据此调整。有效的应用证明应注明使用者身份、版本、资料范围、实际任务、观察结果和局限，由真实参与者确认。模板、老师签名和盖章本身不能替代试用记录；不能在预写证明中填上尚未测出的分钟数、错误数和“显著提升”。

建议形成 1—2 份真实试用记录。外部人员没有实际使用时，材料写“专家评阅意见”，不写“单位已应用”。

## 七、先进性与外部证明怎样补

1. 对照真实同类方法：至少涵盖通用文档问答、常规 RAG 和已有 ESG/财务工具的相关能力。按来源、版本和实际功能比较，不能笼统写“市场没有工具”。自制文献综述不能冒充正式科技查新。
2. 把创新主张写成可检验命题：门禁能否减少特定口径误判且保留正例；A4 能否找到有效反证；通用表格取证能否迁移至未适配企业；证据链能否减少人工回查时间。没有取得结果前使用“拟验证”。
3. 软著按真实权属与要求提交。源码材料完成、提交、受理、登记证书四种状态分别登记；软件修改后核对申请版本。软著不能证明技术先进或业务有效。
4. 发明专利先由学校知识产权部门或具备资质的专业人员评估可保护的技术方案、公开披露影响与权属，再决定是否申请。申请、受理和授权严格区分，不承诺几天取得通知，也不为包装而申请空泛业务方法。
5. 第三方测试若开展，应说明测试对象、版本、项目与方法。老师审阅、实务试用、正式检测、正式查新分别陈述。暂时拿不到认证时，优先把可复核的测试和使用记录做完整。

## 九、最终提交包与答辩验收

学校附件是评分参考，没有逐项规定以下文件均须上传，也未规定科技发明综合报告统一字数或视频时长。先核对申报系统、学院要求及老师通知，再决定上传位置与容量。建议备齐：

- 申报书及资格、成员与贡献、指导教师、课外成果形成时间等确认材料；
- 综合报告：问题与用户、制作方案、关键技术、对照结果、实际试用、局限、团队贡献及参考资料；
- 真实企业案例包：原件索引、逐题运行和引用、人工答案与仲裁、失败及修复记录；
- 性能验证附件与人工比较附件：协议、完整分母、指标定义、原始记录索引，隐去个人信息；
- 操作说明、可运行部署/启动方式、短演示视频、现场失败时清楚标识的历史回放；
- 已真实取得的试用意见、检测/查新材料、软著或专利状态证明，没有则不填“已获”；
- PPT 与作品展示：至少能直观展示一个有证据支持的有效关联、一个合理拒绝/缺证案例及其后续动作。

提交前逐项检查：旧数智会计竞赛获奖层级与是否属于禁止重复申报成果；是否为课程/毕业/学位等被排除作品；成员、导师人数和个人申报件数是否符合通知；历史材料与本次课外新增工作是否清晰。拿不准的具体资格，连同原奖项名称和证明向学校核实，不能自行认定“新增功能后就一定可报”。

答辩材料中每个“更准”“更快”“已应用”都要能点开对应附件。若正式验证结果一般，报告清楚适用题型和失败边界，围绕已经证明的能力陈述；不预设奖项，也不把工程测试通过数量包装成企业样本数。

## 一、可行性评估 ⭐⭐⭐⭐ (85/100)

### 1.1 最大亮点：逻辑闭环终于跑通

V2 最漂亮的一步棋是**把"公开资料不足"从系统缺陷翻转为产品价值**：

- 承接/计划阶段审计师本来就没有内部资料 → 公开资料是这个阶段合理的第一层
- 分析完仍然不够 → 输出"证据缺口 + 待索取资料清单" → 这本身就是产品的核心交付物

这条逻辑是整个方案的"承重墙"，经得起推敲。

### 1.2 需要警惕的落地风险

> [!WARNING]
> 以下四个风险不会让项目"做不出来"，但可能导致**演示效果打折**或**答辩被击穿**。

#### 风险 ① — 10 周时间 vs. 8 条规则的工程量

| 工作项                                               | 真实复杂度                                                                         |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------- |
| PDF 解析（PyMuPDF/pdfplumber）提取三表 + 附注 + MD&A | 年报格式每家公司不同，附注尤其混乱——这一项吃掉 2-3 周很正常                      |
| 8 条交叉验证规则的 prompt 调试                       | 每条规则要把"触发条件 → 原文定位 → 反证 → JSON 结构化"跑通，保守估计每条 2-3 天 |
| 三个 AI 角色流转 + 程序硬校验                        | 光是"质疑 → 反证 → 复核 → 硬门槛拦截"的调试就需要一整周                         |
| 两个案例 × 3 年 × 多维数据整理                     | 人工录入 + 校对，至少 1-2 周                                                       |

**建议**：在 W4 结束前（8 月 10 日），**只跑通 R1（应收/收入背离）和 R2（现金流背离）两条规则的完整链路**，其余 6 条规则先留规则卡文档，代码层面做成可插拔但不急于全部实现。**"2 条跑通 > 8 条跑半"**。

#### 风险 ② — 大模型 JSON 结构化输出的稳定性

计划书要求大模型按严格 JSON Schema 输出（包含原文、页码、认定、正常解释等 10+ 字段）。实测中，即使是最优秀的国产模型，在面对 3000 字以上的年报原文时：

- JSON 格式错误率约 5-15%
- 页码、原文片段的"幻觉"率约 10-20%
- 多字段同时正确的概率会进一步下降

**建议**：

1. 每个 AI 角色的输出都必须经过 `try-except + json.loads()` + 字段完整性校验，失败时自动重试最多 2 次
2. 对"页码"和"原文片段"做**二次程序验证**（用 pdfplumber 反查该页是否真的包含该文本段）
3. 准备一份**预缓存的"黄金标准输出"**用于演示，避免现场崩溃

#### 风险 ③ — T0/T1 隔离的"模型记忆"软肋

计划书提到"提示词禁止调用模型记忆中的案例结论"和"名称去标识化测试"——方向正确，但：

- 提示词禁止 ≠ 技术上不可能泄漏，评委很可能会问"你怎么证明模型不是背出来的？"
- 去标识化测试是好方法，但计划书**没有把它写进十周时间表**

**建议**：把"去标识化对照测试"明确排入 W8 的回测任务，并在方案书中加一句："我们将对案例 A 进行公司名称替换（如替换为'星际动力'），对比去标识前后的输出一致性，验证系统是基于逻辑推理而非模型记忆。"

#### 风险 ④ — "两家案例"的代表性

只有 2 个案例、且都是已有监管结论的公司——评委可能会问："这是不是 overfitting 到两个已知案例？"

**建议**：

- 在方案书或答辩中**主动承认样本量有限**，强调"第一版的目标不是证明泛化能力，而是验证方法论的专业严谨性和工程可行性"
- 如果时间允许，可以加入一家**非舞弊公司**作为反面对照——系统应该能对正常公司输出"未发现明显风险信号"或大幅降级

这种叙事比列表式的"痛点 1、痛点 2"更能打动评委。

### 3.2 一个结构性建议：规则卡应该有版本号

计划书中的 8 条规则（R1-R8）目前是"平铺"的。建议：

1. **每条规则卡增加版本号和最后修改日期**（如 R1 v1.2, 2026-08-15）
2. **规则卡存储为独立 JSON/YAML 文件**，而不是硬编码在 Python 代码中
3. 这样队员 A（审计业务逻辑负责人）可以独立修改规则卡，无需队长改代码

这不仅方便开发，在答辩时也可以展示"规则卡的版本演化历史"，证明团队的迭代过程。

## 四、方案书文本层面的具体修改建议

### 4.1 标题优化

当前标题：

> 审迹智链（AuditTrace）——面向审计业务承接与计划阶段的财务—业务—行业交叉验证智能体

建议精简为：

> **审迹智链（AuditTrace）——面向审计前置阶段的多维交叉验证与证据缺口智能识别系统**

理由：原标题 37 个字太长，且"财务—业务—行业"在副标题中已有。"证据缺口智能识别"点明了杀手级创新。

### 4.2 第三节"评分点对应"可以更有攻击性

当前的表格比较"平铺直叙"。建议改为**问答式**，更像是在提前回答评委质疑：

| 评委可能的质疑                 | 本项目的回答                                                                                            |
| ------------------------------ | ------------------------------------------------------------------------------------------------------- |
| "公开数据不够怎么做审计？"     | 承接/计划阶段本来就只有公开数据。我们的产出不是审计结论，是待核查事项和资料索取清单                     |
| "大模型会编造页码和数字"       | 页码由 PDF 解析程序定位，数字由 Python 复算，模型只负责语义推理。任何硬校验不通过的线索不能进入正式报告 |
| "你怎么证明不是模型背出来的？" | T0/T1 时点物理隔离 + 去标识化对照测试 + 消融实验                                                        |
| "只有 2 个案例能说明什么？"    | 第一版验证方法论的专业严谨性，不宣传泛化准确率                                                          |

### 4.3 第十五节"十周计划"的隐患

W1-W3 是准备阶段，W4 才开始 MVP——这意味着**前 3 周没有任何可运行的代码**。对于 10 周项目来说，这个启动速度偏慢。

**建议调整**：

- W1：定位冻结 + **队长同步搭建空白 Streamlit 项目骨架和数据 Schema**
- W2：专业框架 + **队长完成 PDF 解析和三表提取的 POC（概念验证）**
- W3：数据录入 + **队长完成 R1 规则的端到端原型（哪怕 UI 很丑）**

这样到 W3 结束时已经有一个"能跑"的东西，而不是到 W4 才开始动手。

### 4.4 缺一个"演示兜底方案"的细化

计划书提到"缓存结果、本地数据、模型失败降级和备用录屏"——但**太笼统**。建议：

1. **双轨演示策略**：现场优先跑实时分析，但如果 API 超时或返回格式错误，一键切换到预缓存的"黄金结果"
2. **断网预案**：所有演示数据和模型输出的缓存存储在本地 SQLite，无网络也能完整走完全流程
3. **备用录屏时长**：准备一段 5 分 30 秒的完整录屏，比 5 分钟限制略长，允许剪辑选取

## 一、可行性评估：高（9/10）

**亮点：**

1. **边界清晰，不贪大：** “只做销售与收款循环、只做收入确认、只做2个案例3年数据”——这个克制是项目成功的基础。一个学生团队在10周内不可能做出覆盖所有循环的系统，明确说“不做”比承诺“全做”更专业。
2. **数据源固定可控：** 核心数据只有“年报+公告+同行年报+行业公开资料”，队员B的工作量是可预估的。内部资料作为可选补充，不成为运行前提——这彻底解决了队员之前担心的“数据太多搞不定”的问题。
3. **8条规则有明确锚点：** 每条规则都列了“主要公开资料”来源，队员A不会面对“我从哪里开始”的茫然。例如R3的“产能产量、募投/扩产公告、业务分部”，是可以在年报里找到的。
4. **技术方案克制务实：** Streamlit低代码前端、Python数据处理、国产大模型API、固定案例缓存——这些技术选型都偏保守和可落地，没有一上来就上复杂架构。

**需要关注的执行风险：**

1. **8条规则的数据可得性问题：** 规则R4用“经营范围、成立时间”判断客户背景，这需要企业信用信息公示系统数据。计划书9.1节提到了，但实际整理时如果这数据不好获取，需要提前准备替代方案或降级为“缺失即标证据缺口”。
2. **每周交付任务偏重：** 你们维持了V1的每周交付制度，要求每人每周都有实质产出。这在执行中是好的纪律，但需要队长确保某周某队员考试/生病时的交接预案。

## 二、创新性评估：高（9/10）

**“财务-业务-行业-披露”四维交叉验证是整个项目最大的创新，也是得分点。**

这个设计不是堆砌术语，而是回应了一个真实的审计痛点：审计师在计划阶段最容易犯的错误，不是算错比率，而是看到一个方向就围绕它找证据，忽略了反面解释。

**几个创新点之间的逻辑关系很清晰：**

- 四维交叉验证决定“从哪里发现问题”
- 业务循环驱动决定“问题落在哪个节点”
- 强制反证挑战解决“确认偏误”
- 证据硬门槛解决“AI胡说”
- T0隔离回测解决“事后诸葛亮”

这形成了一个完整的创新闭环，不是零散功能的拼接。

**演示时的高光时刻：** 我建议你们把“消融对比实验”作为演示的压轴。这个设计很聪明——去掉业务/行业维度后系统漏掉了一些风险，加上后又发现了。这比任何理论论述都更有说服力，也直接回应了老师说的“舞弊常是外行从业务逻辑发现”这一点。

V2的架构是模块化的，便于后续扩展：

| 扩展方向                             | 修改难度 | 说明                                                    |
| :----------------------------------- | :------- | :------------------------------------------------------ |
| 增加新规则                           | 低       | 8条规则是模块化的，新增只需加JSON规则定义和资料来源说明 |
| 扩展到采购、薪酬等循环               | 中       | 需新增规则卡和业务节点图，但系统架构不改                |
| 增加案例或实时数据                   | 中       | 需解决数据标准和自动采集问题                            |
| 增加更多内部资料格式兼容             | 中高     | PDF/Excel解析的泛化能力需要持续投入                     |
| 从“预筛查”扩展到“实质性程序辅助” | 高       | 那已经超出竞赛范围和第一版定位，是另一个产品了          |

**计划书8.2节的停止规则非常重要：** 新功能必须“直接服务收入风险、两周内能完成、有验收指标”三条件同时满足，否则延期到“晋级后扩展清单”。这个纪律决定了你们能不能在截止日前交出完整作品，而不会被“再加一个小功能”拖死。

## 五、当前仍需微调的几个细节

以下不是大问题，只是一些可能加分或避坑的小点：

**1. “数据可得性”字段要真的出现在规则卡界面里**

6.2节写了“每条规则都设置资料可得性字段”，这是一个很好的风控设计。建议在原型中把这个字段做得醒目一些。评委看到一条规则因为“产能数据未披露”而标记为“证据缺口”时，会认可你们的严谨，而不是觉得系统能力不足。

**2. 演示案例中的“反证成功”要提前设计好**

如果5分钟演示中所有反证都失败（即所有风险都被证实），反而显得系统有偏见。建议至少有一条风险从“保留”降为“暂缓”，展示反证真的有效，也让评委感觉到系统是平衡的。这也会直接回应老师说的“正常解释同样重要”。

**3. 6.2节R4规则的资料来源建议明确化**

R4提到“官方企业公示信息”，实际指的应该是国家企业信用信息公示系统。5.3节明确写了“不依赖企查查、天眼查等付费数据”——这是对的，但要提前确认免费的官方公示信息能否满足你们的需求。如果无法满足，建议在规则旁注“如客户名称未公开披露或官方信息不可得，此维度标记为证据缺口”，避免现场遇到数据困境。

**4. 队长环节：Vibe Coding日志的保留**

计划书11.2节写了“团队保存需求说明、提示词、AI生成方案、人工修改、测试记录和版本差异”，这是竞赛手册的要求。在实际执行中，队长可以建一个简单的在线文档，每次迭代在同一个地方记录。这不是开发负担，但万一评委质疑“是不是AI全自动生成的代码”，这份日志就是很好的答辩支撑。

## 六、关于指导老师会签的五项确认

计划书第十七节列了五项需要老师确认的事项，我觉得每一条都很合理，老师大概率会通过。但建议在提交给老师时，给每项加一句简洁的“为什么这样设计”：

1. **唯一核心用户为审计师：** “因为我们的质疑—反证—认定—程序逻辑是审计业务语言，转向投资者会丢失专业深度，且伦理风险更高。”
2. **公开资料+内部资料可选：** “因为承接和计划阶段本身就靠公开资料做初步判断，内部资料按缺口补充比承诺全接入更可落地。”
3. **8条交叉验证规则深度：** “规则R1-R8覆盖收入、应收、存货、现金流、产能、客户集中度、行业毛利率和季节性等常见红线区域，每条都映射到认定和程序。”
4. **输出为预审备忘录而非舞弊结论：** “因为公开资料不能替代实质性程序，把‘不知道’写成‘待核查’比强行下结论更专业。”
5. **T0/T1回测替代泛化准确率：** “因为只有2个历史案例，不能计算有统计意义的准确率，隔离回测比一个百分比数字更有说服力。”

## 七、一句话总结

**V2版计划书已经具备执行条件。它的最大优势是：每一个“不做”都有理由，每一个“做”都有边界，每一项创新都有可演示的验证方式。**

建议现在的优先级是：带着这版计划书和五项确认事项去找老师做方向闸门确认，然后立即进入W2，不要再在文档上反复打磨。10周时间充裕但不过剩，代码和数据的执行才是接下来的主要挑战。

你们的准备程度已经远超大部分参赛队伍了。

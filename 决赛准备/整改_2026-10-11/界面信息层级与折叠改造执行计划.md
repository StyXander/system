日期：2026-10-11。工作性质：当前主展示网页的信息层级与交互改造计划。

本文件交付的是执行计划。页面代码尚未按本计划修改，以下执行清单均为待执行；计划交付不代表界面已经实现或通过验收。

## 一、目标与范围

让用户在不展开详情的情况下，看懂本次分析对象、实际计算期间、当前判断、三个独立等级、主要待核查事项及下一步，并能直接找到关键数字的原文入口。让评委通过本次真实结果观察分层等级、三 Agent 协作、认定覆盖、证据用途约束和反向检索的作用。

采用“标题 → 本次结果摘要或紧凑卡片 → 具体的详情入口 → 完整依据”的结构。每个模块选择适合其内容的摘要形式；日志可以只有一行状态，等级可以用三张状态卡，矩阵可以用紧凑表格。不能为了统一样式给每个折叠区强加一段说明。

本轮以根目录 `index.html`、`assets/official-v4/demo-app.js` 和 `assets/official-v4/styles.css` 为实施文件。按实际需要更新 `scripts/check_frontend_contract.mjs` 中的布局约束及相关浏览器验收脚本。修改范围限于呈现、既有结果的读取和必要交互；不调整规则阈值、等级算法、模型、签字、权限、任务恢复语义及正式评价口径。

本轮不新建另一套展示网页，不重做后台，不新增模型生成摘要，不修改封存的历史运行或年报原件。写计划和后续本地实现均不包含提交、推送、部署或对外发布授权。

## 三、目标阅读顺序

### 3.1 首页和进入工作台之前

首页保留简短定位、开始入口、三类交付物和少量特色说明。用现有事实说明“分层安排核查、引用可回查、反向寻找正常解释”，不增加一组没有实际结果的装饰卡。

样本范围、资料截止日说明、代表性接入边界和详细技术解释继续按需展开。来源范围限制在知识底座摘要中可见，完整逐条来源留在详情。

### 3.2 完成运行之后

结果区按以下顺序组织：

1. 分析身份与运行状态：企业、代码、实际计算期间、资料截止日、执行模式、结果完整性。
2. 当前判断与三个独立状态：优先级、证据闭合、金额重要性，附必要理由和限制。
3. 本次待核查事项与关键事实：事项标题、关键数字、缺口、原文核验入口。
4. 质疑、反证、复核的处理过程：各自处理了什么、解释是否待验证、复核保留什么。
5. 认定覆盖与可信控制：紧凑覆盖概览、证据分类、反向检索和数字回查摘要。
6. 下一步资料与程序：优先要做的事，补证及重新评估入口。
7. 完整指标、来源台账、运行留痕和技术详情。

下载和打印操作放在主要结果与下一步附近；查看原文放在对应事实或事项旁。无需滚到日志后才能导出。

桌面右侧“证据追踪轴”保留为定位导航，不再重复一套结果正文。窄屏将其改为简短导航行或常规导航块，不能压缩正文阅读宽度。

## 五、重点模块的具体做法

### 5.1 分层等级：先呈现结果，再展开依据

保留现有六档标签：P1 立即扩大核查、P2 优先核查、P3 常规跟进、P4 维持常规程序、S 暂缓判断、G 暂不分级（资料/口径受限）。保留 E1 已闭合、E2 部分闭合、E3 未闭合。中文含义和代码同时显示，S 与 G 不排列成“高于 P1”的额外档位。

三个轴读取现有 `planning_priority`、`evidence_state` 和 `materiality_display`，沿用当前解释与来源处理。金额重要性单独显示，不参与核查优先级计算；“未评价”不等于不重要。字段缺失时显示“后端未提供”，不按规则状态推导等级。

卡片默认显示轴名、代码与含义、决定状态的简短理由。现有解释若较长，保留决定分级的因素和压制条件；完整解释放入详情，可见理由必须让用户理解暂缓、缺口和未评价。不要用省略号裁掉专业限制。

下方入口分别写“查看优先级判定依据”“查看证据闭合依据”“查看金额重要性说明”。已存在的派生展示来源说明继续可见，不能把页面重建的因子说成后端原始字段。

当前综合关注卡内的六区仍保留完整字段及原始次序，用作完整依据阅读。优先级等卡片只保留一个主显示位置；如果把 `demo-attention-badges` 节点移到结果头部，原第⑥区改为该节点的定位入口和相关完整依据，不再渲染重复卡片。实施前核对六区固定合同、测试与既有签字范围；若合同限制禁止节点迁移，则保留原节点，用同一读取结果生成简短头部读数，内层保留完整依据。选择须记录理由，不能改等级算法或删除因子来适应布局。

### 5.2 摘要形式按内容选择

等级使用状态卡；角色使用短流程；认定覆盖使用表；证据用途使用分类行；日志使用一行概况。不为日志和版本记录再制造多张大卡片。

默认每个角色展示一条核心处理结果，反证可另展示一条不同状态的解释。证据编号和页码用一行元信息表达，完整引用列表进入角色详情。支持关系待复核、角色失败、未执行、建议暂缓等限制始终可见。

事项外露数量以本次结果为准。一个事项必须在展开前就能回答：在核查什么、为什么关注、还缺什么、可以回查哪里。没有事项时明确说明本次未形成待核查线索，并保留规则结果与资料缺口。

反向检索的代表性解释沿用结构化输出的既有顺序，优先展示第一条非空解释并保留其状态；详情保留全部解释。无支持解释时，直接说明未找到当前证据支持的正常解释。没有进入 Agent 路线时显示未执行，不生成解释。

### 5.3 原文入口与程序结果分开解释

企业年报证据支持原文中的披露事实；程序结果卡支持规则计算。一个派生增速或复核主张不能因为引用了年报，就被标为“原文直接证明”。

优先让关键数字的年报输入字段可以直接回查。派生数字同时提供计算口径或程序卡入口。只有本次运行证据提供了有效来源标识与页码时，才显示“查看原文第 N 页”；PDF 页码和印刷页码区分标注。

若当前主张只有程序卡，则显示“查看计算依据”，并在存在真实字段关联时分别提供输入金额原文入口。不为获得可点击按钮随意替换证据，不伪造主张与字段的对应关系。

只有编号而无定位时，直接展示“原文定位缺失”和原因。详情可以列出其他证据，不能暗示这些资料已经证明该主张。核验区的按钮可用状态由当前证据决定，不从旧运行沿用。

### 5.4 减少重复但保留完整材料

当前判断只在主结果头部完整表达一次；下方关注依据和审计计划总览保留独有内容。三角色摘要只使用一个主阅读模块，完整证据仍可从既有抽屉访问。

正文关键数字用于快速阅读，完整指标表用于复算。认定概览用于理解覆盖，详情用于核对证据与程序。来源台账用于说明登记范围，本次证据抽屉用于查当前运行，两者不能混为一份资料数量。

允许摘要与详情少量重复标题、状态及锚点所需上下文，不重复铺陈同一长段落。迁移前保留原文副本，建立“旧模块 → 主显示位置 → 详情位置”清单，逐项确认事实、限定语、原文和功能均可访问。

## 六、折叠交互规范

采用已有原生 `details/summary` 能实现的结构：模块标题和摘要放在 `details` 外，`summary` 紧跟摘要，完整内容位于其下。这样入口处在用户读完摘要的位置，展开后正文顺着阅读出现。无需为了放置按钮增加通用折叠框架。

示意结构如下，内容只是布局说明，不是待硬编码的运行结果：

```text
模块标题
本次状态 / 摘要 / 紧凑卡片
查看完整依据 ▾
  展开后显示完整依据
```

1. 默认只折叠完整依据，核心结果不依赖点击才能出现。进入新运行时清理旧摘要和展开状态。
2. 入口具体命名，例如“查看完整矩阵（本次 N 项）”“查看全部检索记录”“查看完整指标与计算”。只有真实条数可取得时才显示数量。
3. 展开后入口写为对应的“收起…”；原生 summary 的名称需与当前动作一致。既有自定义折叠按钮正确维护 `aria-expanded` 和 `aria-controls`。
4. 同时允许多个详情展开，不强制手风琴互斥，也不展开一个模块就自动关闭其他模块。
5. 模块内最多一层详情。上层整体已取消折叠后，可以保留逐项依据；避免“外层详情 → 角色详情 → 引用详情”连续多层。
6. Tab 可到达入口，Enter/Space 可操作，焦点有明显样式。正文链接与折叠控件分开，不让点击原文误触收起。
7. 展开不自动跳屏；收起长内容时若焦点位于被隐藏区域，应回到控制入口。确需底部收起按钮，只用于明显过长的详情并复用同一状态。
8. 证据追踪轴跳转到详情内目标时，先打开必要的祖先详情，再定位并提供适当焦点；不能滚到隐藏内容的位置。
9. 刷新恢复同一任务时重读该任务真实状态，不创建模型任务；不承诺跨浏览器保存每项展开偏好，不引入额外持久化系统。
10. 详情的打开和关闭只改变显示，不触发模型、写回签字或修改等级。来源台账等已有惰性读取行为按现有合同保留。

## 八、取数、渲染和导出约束

### 8.1 复用现有数据与函数

- `renderAttentionCard` 及现有等级解释函数：用于等级、六区依据和独立轴说明。
- `renderPrimaryReading`：用于事实、当前判断、角色衔接与下一步。
- `renderInnovationControls`：用于矩阵、适配度、数字轨迹和反向检索。
- `renderEvidenceChallenge` 及现有证据定位函数：用于主张、程序卡和原文入口。
- `renderStructuredTable`、`renderSourceLedger`、`renderRunTrace`：保留完整复核材料，外层增加简短概况。
- 重置、新运行、失败渲染、历史恢复以及打印展开/恢复函数：同步覆盖新增摘要和移动后的节点。

优先移动现有节点、拆分必要的渲染段落。仅当摘要和详情确实共享取数时提取小型纯函数；不另造组件框架、摘要服务或状态管理层。

新增节点 ID 必须唯一并纳入现有契约检查。现有 ID 若被测试、打印或事件绑定依赖，尽量保留；必须替换时同步更新引用并记录映射。摘要与详情都读取同一 `run`，禁止拼接不同运行或不同案例的数据。

### 8.2 缺失值与专业状态

没有字段、空数组、未执行检查和真实零值分别处理。不要用 `|| 0` 把未知校验结果变成“0 项未验证”。计数取自本次运行既有记录，未经定义的计数不在前端自创口径。

引用合法性、数字可回查、来源可定位和语义支持分别表达。当前 `semantic_support_status=not_verified` 必须在对应摘要可见，不得因 `support_status` 的历史值把主张标成已经证实。

摘要的中文状态映射不改变原始 JSON。未知状态保留原值并说明未识别，不能默认成功。若发现后端契约缺少必需字段，记录具体缺口；本轮先如实显示缺失，不借界面改造更改专业合同。

### 8.3 打印和导出

JSON、CSV 继续读取同一运行对象，不能因屏幕折叠删掉完整字段。无需为布局调整重写后台 Word 交付逻辑。

打印时展开全部需进入报告的详情，包含等级判定依据、完整指标和专业限制；屏幕摘要与完整内容组织成报告结构，避免重复印两套相同结果。打印前保存各详情原状态，打印完成或取消后恢复。

检查分页、表头、长 ID 换行和固定侧栏；打印件不能出现大面积空白、文字裁切或只有“查看详情”没有正文。固定 AI 声明完整保留：

> AI生成内容，仅供审计计划阶段进一步核查，不构成审计结论或审计意见。

如后续另行生成 Word 计划或验收文件，正文严格为宋体小四，标题为黑体三号；本次仅交付 Markdown 计划。Markdown 中公式仅使用 `$` 和 `$$` 定界符。

### 1.2 50字电梯陈述

> **审迹智链面向事务所审计项目组，用公开资料交叉验证收入风险，输出可追溯待核查线索、资料依据缺口和待索取资料。**

### 1.3 统一术语与边界

| 项目 | 本文统一口径 |
|---|---|
| 核心用户 | 会计师事务所审计项目组，包括项目合伙人、项目经理和负责初步风险评估的审计人员 |
| 三个场景 | 新客户业务承接、续聘复核、审计计划；下文简称“承接、续聘、计划” |
| 核心数据 | 截止分析日已公开的年报、公告、审计报告、监管信息、同行年报及公开行业资料；目标系统支持“官方实时检索”和“本地冻结资料/缓存回放”两种入口，并在界面明确标识 |
| 资料入口 | 输入公司名称、证券代码、分析截止日和期间后，检索模块只从正式披露白名单返回候选资料；用户确认后下载/解析并写入来源台账。检索失败时可切换人工上传或结构化录入，不得用搜索摘要或模型记忆补齐 |
| 内部资料分层 | “待索取资料”是系统生成的需求清单；“补充资料续分析”接收已取得、已授权且脱敏的资料并绑定风险卡局部重跑；“其他内部资料”先进入同一项目的未绑定资料池，人工确认关联后才参与分析，三者不混淆 |
| 风险指标 | 对应规则库 R1—R8（及后续经验收的规则）的指标库；用户可展开查看公式、口径、所需资料和状态并勾选本次范围。核心定义受版本管理，不得自创无规则依据的“舞弊评分” |
| 分析版本 | 每次运行冻结所选规则、参数、数据快照、evidence_id、模型/提示词/Schema版本；新增指标生成新分析版本并重跑受影响风险卡，历史报告只读保留 |
| 目标输出 | 预审风险备忘录、最多5项待核查事项和待索取资料清单；仅计划场景可增加候选管理层认定和建议程序 |
| 明确不做 | 不做投资建议、完整审计平台、舞弊认定、审计意见或自动承接决定 |
| “证据”简称 | 指支持或反驳线索的可追溯资料依据，不等同于形成审计意见所需的充分、适当审计证据；正式界面优先写“资料依据” |
| 状态用语 | “拟/候选”表示设计，“已实现”须有代码与测试，“已验证”须有冻结输入和验收记录；缺原件时标“待核验/UNKNOWN” |

公开资料只是首版最小输入，不表示审计师在上述阶段只能使用公开资料。任何风险线索均须保留正常解释和资料缺口，不能替代函证、检查、访谈或流水核验。

## 二、对指导老师三点意见的具体回应

| 老师的关注 | 本轮对接方式 | 拟在原型中如何体现 |
|---|---|---|
| 使用者到底是谁 | 只面向事务所审计项目组，限定承接、续聘、计划三个场景 | 首页直接进入“新建预审项目”，不设置投资者模式 |
| 审计师需要业务逻辑和完整循环思考 | 以销售与收款循环为主线，把异常连接到业务节点、资料依据缺口和场景化后续动作；计划场景再增加候选认定与程序 | 风险卡可下钻到业务节点、风险机理、待索取资料；计划场景显示候选认定和建议程序 |
| 舞弊线索常来自业务和行业中的“不对劲” | 从单纯财务比率升级为财务—业务—行业—非财务披露的多维交叉验证 | 增加交叉验证矩阵，展示一条线索由哪些维度共同触发 |

老师同意团队开始推进后，上表作为本项目的**设计基线**继续保留；它说明团队准备如何回应老师意见，不代表相应页面、规则或效果已经完成验证。

这次修改不把项目扩成“万能审计系统”，而是把一个小场景做深：**在有限时间和有限公开资料下，帮助审计师更系统地提出高质量风险假设，并明确下一步要向客户索取什么证据。**

### 3.2 与常见做法的计划差异

下表是方案层面的功能对照，不代表对所有商业产品或研究文献作穷尽性评价；正式方案书引用具体产品或论文前，仍须回到原件核验。

| 典型做法 | 主要长处 | 常见局限或不覆盖项 | 本项目拟验证的差异 |
|---|---|---|---|
| 传统财务比率/红旗规则 | 计算透明、容易复算 | 通常停留在指标异常，业务解释、反证和后续资料需求依赖人工补充 | 将确定性指标连接到销售循环、正常解释、资料缺口和分场景动作 |
| 通用大模型直接阅读年报 | 语义理解和摘要能力强 | 若无外部约束，引用、页码、数字和输出稳定性难以作为可复核记录 | 模型只处理语义；程序回填证据ID、原文、页码和计算，并以硬门槛阻断缺项输出 |
| 典型事务所数据分析平台 | 可处理更丰富的内部数据和审计流程 | 往往依赖组织数据、专有系统和实施条件，不是本竞赛四人团队的替代目标 | 以公开资料形成轻量预筛闭环，把无法回答的问题转成待索取资料 |
| 审迹智链拟议方案 | 专业规则、语义推理、结构化反证和来源约束组合 | 当前只覆盖有限案例、收入主题和首批规则，尚待实现和验证 | 主打可追溯证据硬门槛、一次反证、资料缺口产品化及T0/T1隔离，而非宣称底层模型或算法首创 |

### 3.3 评委可能质询与拟验证回应

| 评委可能质询 | 本项目的拟回应与验证方式 |
|---|---|
| “公开资料不够，怎么服务审计？” | 三个目标场景可以先用公开资料形成风险假设；目标输出是资料依据缺口、待核查事项和待索取资料，不是审计结论 |
| “大模型会编造页码、原文和数字。” | 页码和候选原文由解析程序提供，数字由程序计算；模型输出须经JSON Schema、原文反查、字段和禁用词校验，未通过只能留在草稿区 |
| “如何检查模型是否受历史案例记忆影响？” | 在正式回测前冻结T0/T1，隔离T1后验材料，并安排公司名称与证券代码去标识化敏感性对照；保留输入清单、版本和运行日志。该方法只能降低和检查风险，不能单独作出不存在记忆影响的证明 |
| “只有2个案例能说明什么？” | 第一版只验证方法论的专业严谨性与工程可行性，报告覆盖、引用、稳定和失败情况，不宣传泛化准确率或普适舞弊识别能力 |
| “10周能否完成8条规则？” | 先跑通R1、R2的端到端链路；R3—R8按资料可得性和阶段验收逐条接入，未通过的规则保留为规则卡，不包装成已实现功能 |

## 四、目标用户、使用场景与产品价值

### 4.1 用户故事（待测试）

项目经理在首次客户风险讨论前，需要从多年度年报、收入政策、应收、现金流和同行资料中形成初步风险画像。系统拟先展示资料可得性，再给出不超过5项可下钻到原文、计算、正常解释和资料缺口的待核查线索。用户可在风险总览/风险卡上**勾选本次关注的风险指标**（对应已实现规则，默认建议勾选触发项），并在取得客户或内部授权的补充资料后，通过**续分析窗口**把资料发给系统、指定关联风险卡后继续分析。节省时间和改善程度须经后续人工对照测试，本版不预设效果数字。

### 4.2 三个场景的输出差异

| 场景 | 系统拟提供 | 不替用户做什么 |
|---|---|---|
| 承接 | 潜在客户收入模式、历年变化、同行差异、公开监管事项及需进一步了解的问题 | 不决定是否承接、定价或团队配置 |
| 续聘 | 本年新增变化、资料缺口和风险讨论输入 | 不自动决定是否保持客户关系和审计业务 |
| 计划 | 待核查事项、候选管理层认定、待索取资料和供考虑的建议程序 | 不替代审计人员选择程序或形成审计结论 |

### 4.3 核心痛点与价值

公开资料分散、比率异常难以落到业务节点、分析者可能忽略正常解释、通用模型输出不一定可复核，而公开资料又无法回答全部问题。本项目因此不追求“自动判定”，而是把异常转成**有来源、有反证、有资料缺口和下一步资料需求**的预审任务。统一责任边界见§1.3。

### 5.2 第一版明确不做

- 不做投资建议、公司估值、全市场实时扫描或完整审计平台；
- 不覆盖所有舞弊类型、全部审计循环或任意内部资料格式；
- 不鉴定合同、发票、流水真实性，不做全网交易关系图谱；
- 不输出舞弊概率、舞弊定性、审计意见或监管结论；
- 不现场分析未经预检和合规确认的真实公司，不以付费数据库作为运行前提。

### 5.3 两类资料的边界

公开资料构成首版最小闭环；内部资料仅为核心闭环稳定后的条件项。竞赛演示只使用公开、模拟或合法脱敏样例，不接触真实客户机密。具体来源和授权字段见附录B。

### 5.4 最小可演示闭环（范围下限）

即使自动PDF抽取或多规则扩展失败，第一版也必须优先实现：

> **1个 DEV_T0 开发样例 × R1当前工程版 × 人工结构化录入数据 → 确定性计算 → 一轮质疑/反证/复核 → 引用与公式硬校验 → 人工确认 → 1张风险卡草稿及待索取资料。**

人工录入不是临时补救，而是首版受支持的降级路径；录入值仍须绑定文件、披露日期、页码和原文，并由另一成员复核。该闭环能运行只证明开发样例上的工程可行性，不等于正式案例、完整原型或效果验证。

### 5.5 分阶段实现门槛

| 阶段 | 最小范围 | 进入下一阶段的验收条件 |
|---|---|---|
| M0 技术探路 | 空白Web骨架、核心数据Schema、一个年报PDF解析POC及人工录入兜底 | 能记录文件、披露日期、页码、单位和解析状态；失败时可转人工结构化录入 |
| M1 单规则最小链路 | 运行§5.4定义的最小闭环 | 计算可复算、原文可反查、字段完整；无资料依据时只能输出缺口或暂缓 |
| M2 双规则MVP | 在M1基础上加入R2，并跑通质疑、反证、复核、硬校验和人工确认；界面支持用户勾选本次分析的风险指标（至少R1/R2） | R1、R2均通过固定样例回归；取消勾选后该指标不进入导出；失败模式和重试/降级日志可查看 |
| M3 规则扩展 | R3—R8按资料可得性和业务价值逐条接入；新规则通过验收后才出现在可选指标列表 | 每增加一条规则，都须有版本化规则卡、测试样例、正常解释、失败样例和人工复核；否则只保留为文档规则、界面灰显 |

| M4 正式评估 | 冻结案例、T0、基线、模型、提示词、指标和预算后运行回测 | 简化Research Contract经人工确认；T1保持锁定直至全部预登记T0运行完成且预测与日志固定 |

“8张规则卡”是专业规则库目标，不等于第一版必须同时完成8条代码链路。执行优先级始终是**一条完整、可复核的链路优于多条半成品规则**。

### 5.6 两条交付线：48小时快速MVP与竞赛级版本

团队可以在一两天内用 Python、一个公开年报、R1当前工程版确定性计算和一次模型连通检查做出“能运行的Demo”。这条快速MVP只用于尽早验证产品方向，不代表已经完成竞赛级系统。

但“能跑”与“可作为竞赛成果”不是同一个验收标准。竞赛级版本还必须补齐来源可回指、官方资料白名单、T0/T1时点隔离、失败关闭、正常解释与反证、人工确认、指标选择记录、补充资料权限和重复运行日志。计划书后续周次主要用于这些可复核性、专业性和评估工作，而不是把第一次写出网页故意拖到最后。

快速MVP的最低验收顺序为：

> **D1：**本地年报入口 → R1当前工程版四字段录入/回指 → 公式计算 → 风险卡草稿；
>
> **D2：**来源编号/页码回指 → 候选指标范围记录 → 模型连通检查或明确 `config_missing` → 人工确认提示；
>
> **D3以后：**先完成三Agent固定链、真实有效Key运行和故意失败样例；R2工程版已提前接入，但仍须完成专业阈值复核与同口径回归；之后再接入 RAG、导出、资料中心和评估。

若快速MVP先用本地资料，页面必须显示“本地冻结资料/缓存回放”，并把官方实时检索标记为未接入；快速MVP不能直接被表述为已完成的正式系统。

### 5.7 从现在到9月的交付收敛：一条主链、三个优先级

本项目不再把“做一个网页”“再补一个Agent”“最后再接后端”分成互不相连的愿望。当前开发围绕一条可启动主链推进；其中未接入的环节必须标为目标，不得提前作为已实现能力演示：

> **根目录展示网页 → Python API → 已核验资料包 → 程序计算 R1当前工程版 → 质疑Agent → 反证Agent → 语义复核Agent → 程序硬校验 → 人工确认/缓存回放。**

每周结束时必须能从上一周版本继续运行；新功能只有在不破坏该主链时才允许合入。任何“只做页面、没有后端”“只调模型、没有证据回指”或“只有文字说明、没有可复现输入”的成果，均不算通过本周阶段门。

| 优先级 | 交付范围 | 进入条件与边界 | 暂不作为阻塞项 |
|---|---|---|---|
| P0：可运行主链 | 1个 DEV_T0 开发样例、连续3年字段、R1当前工程版、真实或明确报错的模型调用、三角色固定链、JSON Schema、来源/公式硬校验、人工确认、单命令启动说明和至少1个失败样例 | 后端必须接到根目录 `index.html`；密钥不得出现在前端；每次运行须留下版本和日志。R2工程版虽已接入，P0未通过时仍不扩展到R3—R8、RAG或第二案例 | R3—R8、复杂同行库、任意格式内部资料上传 |
| P1：可提交演示 | R2或同等第二条规则、候选指标范围与实际运行结果一致、交叉验证矩阵读取运行结果、待索取资料、一页备忘录导出、缓存/失败状态；**RAG V1为团队终版固定目标** | RAG只在 G5 主链通过后启动；完成时须可回放检索并回查 `evidence_id`，未通过不得把它写成已实现 | 开放式聊天、实时全网搜索、完整审计平台 |
| P2：条件功能与评估 | 官方实时检索适配器、受控补充资料续分析、更多已验收规则、第二案例与有限T0/T1评估 | 只能在P0稳定且不挤占RAG/主链修复时开始；失败可延期并明确标“未完成” | 为了数量强行凑8条规则或B0—B3全套实验 |

**9月最低可运行定义（P0）：**在一台未存密钥的演示电脑上，按README完成依赖安装与 `.env` 配置后，能启动本地服务；能选择 DEV_T0 样例、复算 R1当前工程版、回查来源并展示“模型成功 / 配置缺失 / 调用失败”等真实状态；三角色输出和硬校验日志可查看；人工确认保留为人做的步骤。R2当前工程版已可同行运行，但P0不以“多一条规则”替代真实三Agent验收。**团队终版目标（P0通过后完成P1）：**在不破坏P0的前提下，完成R2专业复核、RAG V1可回放检索和一页备忘录导出。若P1或P2未实现，页面和材料必须如实隐藏或标注，不能倒灌为P0已完成。

## 六、专业主线：销售与收款循环的初步风险评估

### 6.1 业务循环不是“把所有资料都接进来”

系统拟用销售与收款循环帮助审计师定位问题，但只做到计划阶段需要的深度：

> 客户与信用政策 → 合同/订单 → 发货或提供服务 → 验收/控制权转移 → 开票与收入确认 → 应收账款 → 回款、退货和折让

公开资料通常不能证明每笔交易是否真实，因此系统不作交易级结论。三类场景的输出差异统一按§1.3和§4.2执行。

### 6.2 八条候选交叉验证规则（分阶段实现）

下列R1—R8目前是团队拟定的专业规则库v0.1，尚待逐条专业复核和工程验证。**当前网页/后端实现了R1/R2两条工程版：**R1在来源闸门通过时比较本年与上年应收账款增速、营业收入增速及其差额；R2比较收入增速与经营活动现金流量净额增速，并显示净利润增强项。两者都不包含周转天数、合同资产、持续性判断或业务节点级证据。完整R1/R2仍须补齐字段、阈值口径并经人工复核后才可取代当前工程版；R3—R8只有在所需资料可得、不会挤占核心链路且通过单条验收时才进入原型。

| 编号 | 交叉验证规则与通俗解释 | 主要公开资料 | 关联认定与下一步 |
|---|---|---|---|
| R1 | **完整专业规则（待复核、未实现）：**应收账款增长持续快于收入且应收账款周转天数上升，或合同资产/收入占比持续上升：收入增长与结算、回款或履约条件之间存在需核查的不一致。当前工程版只实现其中“四字段增速背离”方向判断 | 三张主表、附注、信用政策披露；当前工程版仅需四个金额字段及其来源定位 | 候选认定包括收入发生及应收/合同资产存在、权利和义务、计价和分摊，须按具体信号选择；索取账龄、期后回款和主要合同摘要 |
| R2 | 收入增长与经营活动现金流表现持续背离，且结合经营性应收应付、存货、税费和结算周期后，T0公开资料仍未提供可核验解释 | 现金流量表、利润表、资产负债表、管理层讨论 | 仅作为收入发生/截止及相关资产计价的辅助线索；索取销售明细、期后回款和大额异常交易清单 |
| R3 | 在产品、期间、单位、合并范围及产销存口径可比的前提下，产品销量或收入规模与公开披露的设计产能、产量存在需进一步解释的差异 | 年报产能产量、募投/扩产公告、业务分部 | 候选认定为收入发生、准确性；核对产销存、委外生产、产能利用及口径差异说明 |
| R4 | 前五大客户集中度发生明显变化，或主要交易对手公开登记特征与披露交易规模存在需进一步解释的差异 | 前五大客户披露、公司公告、官方企业公示信息 | 收入发生；关联方关系及交易的完整性和列报；登记特征不能单独证明交易无商业实质或存在关联关系，须索取客户清单、合同、验收和函证资料 |
| R5 | 针对具体交易，以转让前是否控制特定商品或服务为核心，结合合同权利义务、履约责任、定价和存货风险等事实；披露不足或可比同行口径不同只触发“总额法/净额法判断依据待核查” | 收入政策附注、同行年报/招股书、业务模式 | 候选认定为准确性、分类和列报；检查合同权利义务并先确认交易是否可比，不据单一事实自动判定列报错误；正式用语须回收入准则原件核验 |
| R6 | 在产品结构、成本范围、会计政策和期间口径可比的前提下，公司毛利率逆行业趋势明显上升，但公开资料没有给出可核验的产品、技术、品牌或成本解释 | 分部毛利率、同行年报、行业公开统计 | 候选认定为收入准确性及存货/成本计价和分摊；索取产品毛利表、成本结转和价格变动资料 |
| R7 | 管理层讨论称竞争加剧、价格承压或需求下降，但相关分部收入/毛利率反而显著改善且公开资料未解释 | 管理层讨论与分析、分部附注 | 首先作为披露一致性线索；再由人工判断是否涉及准确性或列报，并检查价格、销量和成本资料 |
| R8 | 在T0前已公开且口径一致的资料中，第四季度或年末收入占比显著高于历史/可比同行，同时截至T0可观察的应收、合同资产、退货折让或减值信息出现需共同解释的异常 | 分季度经营数据、应收/合同资产附注、T0前退货折让或减值披露 | 候选认定为截止、发生；索取年末前后销售明细、发运验收、退货和期后回款资料。T0后首次公开的信息只能进入T1后验对照区 |

每条规则都设置“资料可得性”字段，并在界面醒目标记“可得、部分可得、不可得”。若公开资料没有披露产能、客户身份或交易细节，系统不得臆测，只能把该项标记为“不可评价/资料依据缺口”，并生成待索取资料。尤其对R4，只有客户名称已公开且官方登记信息可以回到原始页面时才作交叉核对；名称未披露或官方信息不可核验时，不得以搜索摘要、付费平台片段或模型记忆补齐。规则是风险筛查工具，不是自动定罪标准。

表中管理层认定均为候选映射，不表示异常已经导致错报。规则卡须区分交易类别、期末账户余额和列报层面的认定，由人工按具体风险选择，不机械全选。

规则卡拟采用独立JSON/YAML管理，字段和状态见附录A。任何状态升级须有测试或人工复核依据，避免把候选规则误认为已上线功能。

### 6.3 专业映射矩阵

每条风险的共同字段按以下结构展开：

> **业务循环节点 → 异常信号 → 风险机理 → 受影响报表项目 → 正常解释候选 → 资料依据缺口 → 场景化后续动作**

规则卡内部保留“候选管理层认定—待索取资料—建议程序”映射；页面是否展示按§4.2控制。

例如，“应收增长快于收入”本身不是结论。目标流程还要检查是否由新增大客户、结算周期改变、季节性或行业账期普遍拉长导致；如果公开资料不能区分风险解释与正常解释，则标记“资料依据不足—待补充”或“暂缓”，并列示资料需求。只有存在可追溯支持且经人工复核时，才可进入Top 5待核查事项。

## 七、拟验证的五项核心创新

五项均属于专业流程、方法与工程约束创新，不主张训练了新的基础模型或提出新的底层算法；相对定位见§3.2。

### 7.1 创新一：财务—业务—行业—披露多维交叉验证

系统拟不只看比率，而是把四个维度放进同一条质疑链：财务数字是否勾稽、业务规模是否合理、行业惯例是否一致、管理层文字与报表结果是否一致。界面拟用“交叉验证矩阵”展示一条风险由哪些维度触发。多维触发只增加待核查信息量，不自动提高风险等级；待核查优先级还须结合潜在金额影响、发生可能性、资料质量、正常解释和人工判断。

拟议矩阵最小草图如下，实际状态只能由可追溯资料填充：

| 待核查事项 | 财务 | 业务 | 行业 | 披露 | 资料缺口 |
|---|---|---|---|---|---|
| R1应收—收入背离 | 已支持/不支持/不可得 | 同左 | 同左 | 同左 | 账龄、期后回款、主要合同摘要等 |

### 7.2 创新二：业务循环驱动的证据缺口与资料索取

系统目标不是发现异常后停在一句提示，而是把风险落到销售与收款循环节点并生成对应的资料需求，按§4.2控制不同场景的输出。这样把公开资料的局限转化为“知道下一步需要取得什么资料依据”的拟验证产品价值。

### 7.3 创新三：证据硬准入门槛

目标架构要求每张正式风险卡必须包含来源、披露日期、原文、财务数字、公式、资料依据缺口和场景化后续动作。PDF和网页的定位字段见附录B。大模型拟负责语义判断，程序拟负责来源定位、原文、公式、必填项和禁用词硬校验；任何关键项缺失，该线索只能保留在草稿区。

### 7.4 创新四：一次结构化强制反证挑战

目标流程中，质疑模块提出风险假设后，反证模块必须在允许使用的资料中检索并记录正常解释候选及其支持或缺失资料；未检索到时明确写“未检索到可核验支持/待补充资料”，不得为了满足格式补造解释。语义复核模块只能作“保留、降级、暂缓”判断，不能自由发挥形成无休止辩论。最终仍由程序硬校验和审计师人工确认把关。

### 7.5 创新五：降低并检查后验信息泄漏风险的时点隔离回测

系统拟以T0为分析截止日，只允许使用T0前已公开的资料；后续问询关注、公司回复、更正和最终监管结论按类型放在隔离的T1后验对照区，全部T0运行及日志锁定且获得人工授权后才解锁。同时比较“只看财务数据”与“财务—业务—行业交叉验证”的结果，评估新增维度在冻结历史案例上是否提供增量线索，而不把有限案例结果外推为普适能力。该设计只能降低和检查泄漏风险，不能证明研究者或模型完全没有历史记忆。

## 八、拟实现的完整工作流程与稳定化设计

### 8.1 目标主流程（当前R1/R2工程版已接入确定性计算、来源闸门、日志与人工复核；真实Agent成功运行待Key验收）

1. 审计师新建预审项目，输入公司名称/证券代码，选择分析截止日、目标期间、行业和业务场景；
2. 用户选择“官方实时检索”或“本地资料/缓存回放”；系统返回或读取候选资料，并完成来源、日期、页码、单位和可读性预检；
3. 程序抽取/接收结构化字段，计算确定性财务指标，建立多年度趋势；
4. 界面展示**风险指标列表**（映射已实现规则；首批仅为R1、R2，R3—R8在通过验收前以“候选/不可选或仅说明”展示）。系统给出默认勾选建议（通常为触发项），**审计师可增删本次运行/导出的指标**；未勾选的指标不进入质疑链，也不写入正式Top 5；
5. 系统保存本次 `analysis_run` 的规则、参数、数据快照和来源范围；
6. 交叉验证引擎仅对用户勾选且“已实现且通过验收”的规则连接财务、业务、行业和披露信息；
7. 质疑智能体生成结构化风险假设；
8. 反证智能体寻找正常解释和反对证据；
9. 语义复核智能体判断保留、降级或暂缓；
10. 程序硬校验引用、页码、公式、必填字段和禁用词；
11. 审计师人工确认，并按§4.2生成分场景输出和报告版本；
12. 若后续取得授权补充资料：在**补充资料续分析窗口**上传或粘贴结构化摘要，选择关联的风险卡/风险指标，完成授权与脱敏预检后，**仅重跑对应风险卡**（不默认全量重算全部指标）；历史评估时须先完成并锁定全部T0运行和日志，再由授权人解锁T1后验对照材料。

#### 8.1.1 风险指标用户自选（拟实现）

| 要点 | 口径 |
|---|---|
| 指标是什么 | 与规则卡一一对应（如 R1 应收—收入背离、R2 收入—现金流背离）；一张风险卡可挂多个相关计算子项，但**可选粒度以 rule_id 为主** |
| 谁来选 | 审计师；系统可给“建议勾选”，不强制全选，也不因未勾选而编造该指标结论 |
| 默认策略 | 新建项目时默认勾选当前已实现且资料可得的规则；若某规则资料不可得，默认不勾选并显示“资料不足” |
| 禁止项 | 禁止用户自定义无规则依据的“舞弊概率/造假分”；禁止对未实现规则输出正式风险卡 |
| 当前状态与最小版本 | R1/R2已可勾选并实际影响后端运行、来源台账与风险卡草稿；R3—R8不生成风险卡。每次运行已保存独立 `run_id`，但版本差异界面与导出范围尚未实现 |

#### 8.1.2 补充资料续分析窗口（拟实现）

| 要点 | 口径 |
|---|---|
| 入口 | 风险卡下钻页、资料缺口/待索取资料页提供“取得补充资料后继续分析”入口，打开续分析窗口（可与主界面同页侧栏或独立面板） |
| 用户做什么 | 选择关联风险卡/指标 → 选择资料类型（合同摘要、销售明细摘要、发货/验收摘要、期后回款及退货摘要等）→ 上传模板文件或粘贴结构化字段 → 确认授权与脱敏 → 提交“继续分析” |
| 系统做什么 | 预检公司/期间/单位/字段/授权 → 将补充资料写入该卡的 evidence 集合（带新 evidence_id 与来源台账）→ **只重跑该卡的质疑—反证—复核—硬校验** → 更新正常解释、资料缺口与待索取清单版本 |
| 明确不做 | 不做开放式闲聊客服；不因上传资料自动认定舞弊或撤销全部历史草稿；不允许补充资料绕过禁用词与人工确认直接导出 |
| 阶段条件 | 核心公开资料链路（至少 R1 最小闭环）稳定后开发；G6 前核心链未稳则顺延，不影响主交付 |

#### 8.1.3 公开资料获取与解析双模式（拟实现，但属于目标产品必备入口）

| 模式 | 用户动作 | 系统动作 | 必须留下的记录 |
|---|---|---|---|
| 官方实时检索 | 输入公司名称、证券代码、分析截止日和目标期间，确认候选资料 | 检索交易所、上市公司官网、巨潮等白名单；返回标题、URL、披露日、期间、资料类型和可读性；用户确认后下载并解析 | 查询时间、URL、下载时间、文件哈希、解析状态、候选/确认人 |
| 本地导入/缓存回放 | 选择已放入项目目录的PDF或结构化模板 | 校验公司、期间、单位、文件哈希和来源台账；沿用已核验字段；页面明确显示“本地资料”或“缓存回放” | 文件名、路径或URL、披露/下载日期、页码、原文、evidence_id、缓存运行版本 |
| 解析失败降级 | 改用人工结构化录入并上传原件定位信息 | 不让模型猜数字、页码或原文；字段完整后才允许进入确定性计算 | 人工录入人、复核人、原件页码、解析失败原因和修复状态 |

检索智能体可以提出候选关键词、候选文件和正常解释，但不能把搜索摘要、论坛内容或模型记忆直接写成正式资料依据。官方检索结果必须经过来源白名单、期间/T0过滤和用户确认；只有通过预检的资料才进入字段抽取和后续AI链路。当前静态网页仍处于本地样例模式，不能把本节写成已上线功能。

#### 8.1.4 指标库、受控口径与分析版本（拟实现）

指标库按“已实现可选、规则草案灰显、资料不足不可选”显示。每个指标至少展示：`rule_id`、指标名称、一句话解释、公式、单位、期间、可比条件、默认是否建议勾选、所需资料、触发/暂缓条件、关联风险卡和规则版本。用户可以选择本次运行范围，也可以在受控范围内选择期间、同行集合或阈值参数；改变核心定义或公式必须生成新规则版本并由专业人员确认。

每次分析生成一个不可变的 `analysis_run` 记录，至少冻结：

- 用户勾选的 `rule_id` 集合及参数口径；
- 数据快照、来源台账和所有 `evidence_id`；
- 规则、程序、模型、提示词和Schema版本；
- 运行时间、资料范围（公开/请求补充/其他内部）和人工确认状态。

新增指标时不得只在旧报告末尾拼接一句话。系统应重新计算受影响的确定性指标，并对受影响风险卡重新执行质疑—反证—语义复核—硬校验，生成新的报告版本；旧版本保留只读。若新增指标与某张风险卡无关，则该卡可保持原内容，但风险总览、排序和综合备忘录仍应按新版本重新生成。若指标缺少可核验资料，状态为“暂不计算/资料依据缺口”，不能由AI估算。

最小验收：同一数据快照先只选R1生成V1，再加入R2生成V2；V1不变，V2能显示新增规则、受影响卡片、重算结果和新旧差异。

### 8.2 三类AI角色不是自由辩论

本节是目标架构和开发合同。当前网页中的三角色仅为职责说明卡，后端模型调用目前只做连通检查；在同一 `evidence_bundle` 上留下 `challenge.json`、`counter.json`、`review.json` 和校验日志之前，不得表述为“已实现多智能体工作流”。

| 角色 | 只能做什么 | 不能做什么 |
|---|---|---|
| 质疑角色 | 按专业规则提出风险假设并引用证据 | 无证据猜测主体动机或直接认定舞弊 |
| 反证角色 | 检索正常解释候选、相反资料和缺失资料；未找到时明确记录 | 为了“辩护”或满足字段而编造事实 |
| 语义复核角色 | 检查证据是否支持措辞并给出保留/降级/暂缓 | 绕过程序硬门槛直接批准导出 |

在目标架构中，确定性计算、日期过滤、字段完整性、禁用词和引用定位将由程序完成。AI只处理语义和专业推理，人工拥有最终确认权。

### 8.3 结构化输出、证据绑定与失败关闭

模型拟只返回“schema_version、run_id、rule_id、风险假设、evidence_id、正常解释候选、资料依据缺口、建议状态和场景化后续动作”等结构化字段。披露日期、T0标签和原文由程序依据evidence_id回填；PDF来源回填文件名、PDF页码和印刷页码，网页来源回填URL、页面标题、查询/抓取日期及存档哈希或定位信息。模型不得自由生成定位信息或改写后冒充原文。

拟定校验顺序为：**JSON解析与Schema校验 → 证据ID存在性 → T0日期白名单 → 规范化原文反查 → 数字来源与公式复算 → 必填字段与禁用词 → 人工确认**。解析或Schema失败最多自动重试2次；仍失败则记录“MODEL_OUTPUT_INVALID”并停止导出。PDF解析不稳定时，按§5.4转入受支持的人工结构化录入路径，来源、页码和原文仍须反查。上述机制通过有效和故意错误样例验收后，才能表述为已实现。

### 8.4 Agent运行合同：谁输入、谁判断、谁拦截

三角色不是三个自由聊天窗口，也不允许把200页年报全文直接塞给模型。一次规则运行由后端按下图固定编排；每个箭头都产生可保存的JSON和日志。

```text
来源台账 / PDF页级文本 / 人工结构化字段
                    │
                    ▼
程序预检：T0、单位、页码、evidence_id、字段完整性
                    │
                    ▼
程序：R1/R2确定性计算 + 触发/暂缓判断 + evidence_bundle
                    │
                    ▼
质疑Agent（提出待核查假设，不能作事实认定）
                    │  challenge.json
                    ▼
反证Agent（用同一证据包寻找正常解释、相反资料和缺口）
                    │  counter.json
                    ▼
语义复核Agent（只在 retain / downgrade / defer 中建议）
                    │  review.json
                    ▼
程序硬校验：Schema → evidence_id → T0 → 原文 → 公式 → 禁用词
                    │
                    ▼
人工确认 → 风险卡 / 缓存回放 / 预审风险备忘录
```

| 环节 | 程序负责（不可交给模型） | Agent负责（必须结构化返回） | 失败后的状态 |
|---|---|---|---|
| 资料预检 | 文件哈希、公司/期间、T0、披露日期、PDF/印刷页、单位、字段缺失 | 不参与 | `SOURCE_INCOMPLETE`，只显示资料缺口 |
| R1/R2计算 | 数字抽取确认、单位换算、公式、阈值、是否触发 | 不得重新计算或改写数字 | `RULE_NOT_TRIGGERED` 或 `DATA_GAP` |
| 质疑Agent | 组装规则说明、已触发的计算结果和证据包 | 提出“待进一步了解”的风险机理；每个判断绑定已有 `evidence_id` | `LLM_UNAVAILABLE` 或 `MODEL_OUTPUT_INVALID`，保留程序结果，不生成AI复核卡 |
| 反证Agent | 把质疑结果和同一证据包传入；不追加未核验网页搜索结果 | 给出正常解释候选、支持/反对证据和仍缺资料；允许明确“未检索到可核验支持” | 同上；不得用默认乐观解释代替失败 |
| 语义复核Agent | 传入前两步JSON和证据包；限定状态枚举 | 仅建议 `retain`、`downgrade` 或 `defer`，检查措辞是否超出证据 | 同上；风险卡保持“待人工处理” |
| 硬校验 | 校验Schema、ID、页码、原文、公式、禁用词、版本 | 不参与 | `VALIDATION_FAILED`，停止导出 |

**开发预算（先固定上限，再以W2实测调整一次）：**每个规则运行最多调用3次；证据包最多6个文本片段、每段不超过600个中文字符，并始终携带4项结构化财务字段。质疑/反证/复核的最大输出分别为700/700/350 token；每次实际输入、输出token、耗时、模型ID和重试次数必须写入 `analysis_run`。超过上限时由程序裁剪到已登记的片段清单，并记录未送入模型的片段，不能静默截断后假装模型读过全文。

### 8.5 统一JSON Schema与状态机（开发第一版）

所有角色使用同一份 `agent_output_v1` Schema；程序拒绝自由文本、Markdown结论或未登记的证据ID。最小结构如下，正式实现时以Pydantic/JSON Schema生成校验器并写入仓库：

```json
{
  "schema_version": "agent_output_v1",
  "run_id": "RUN-2026-...",
  "role": "challenge|counter|review",
  "rule_id": "R1",
  "status": "candidate|retain|downgrade|defer",
  "claims": [
    {
      "text": "待进一步了解的表述，不能包含舞弊认定",
      "evidence_ids": ["STD_REV_2025", "STD_AR_2025"]
    }
  ],
  "normal_explanations": [
    {"text": "正常解释候选或未检索到可核验支持", "evidence_ids": []}
  ],
  "data_gaps": ["账龄明细", "期后回款记录"],
  "requested_materials": ["账龄明细表"],
  "reason_for_status": "仅基于本次证据包的简短说明"
}
```

`run_id`、`role`、`rule_id`、`status`、至少一条 `claims`、每条claim的非空 `evidence_ids` 为必填项。`evidence_ids` 必须属于本次 `evidence_bundle`；`data_gaps` 和 `requested_materials` 只能来自该规则卡允许的词表或人工确认的模板。程序回填原文、文件名、页码、披露日和计算结果，模型输出里出现这些定位字段时一律忽略并记录审计日志。状态迁移固定为：`candidate → retain/downgrade/defer → human_confirmed 或 human_returned`；模型没有“确认”“导出”“舞弊”等状态。

### 8.6 RAG知识库：受控、可回查的检索增强，不把全文交给LLM

RAG V1是团队终版的**必做功能**，但不是当前R1主链尚未通过时的并行战线：只有G5完成“R1当前工程版→三Agent→硬校验→人工确认草稿”的可回放链路后，才启动RAG实现。它不是把年报全文塞进模型，也不是让模型联网搜索。知识库只收录已通过来源白名单、期间/T0预检和人工确认的资料。每个返回给模型或展示给审计师的片段，都必须能回到原文件和页码。

RAG V1固定按以下链路实现：

> **资料确认 → PDF按页提取 → 按标题/表名切成短片段 → 写入来源台账与SQLite → 生成向量并建立本地FAISS索引 → 规则关键词与向量混合检索 → 返回带 `evidence_id` 的片段 → 构建 `evidence_bundle` → 三Agent与程序硬校验。**

| 环节 | RAG V1必须实现 | 必须保存 | 明确禁止 |
|---|---|---|---|
| 入库 | 年报、公告、监管/行业资料及已授权补充资料先经过来源、T0、公司/期间和文件哈希预检；同一资料不重复入库 | `source_id、文件哈希、资料类型、披露/下载日、T0标签、确认人` | 搜索摘要、论坛、自媒体、付费库片段或模型记忆直接入库 |
| 切片 | 先按PDF页，再按标题、表名或自然段形成短片段；每片段关联原页和必要的前后文 | `evidence_id、source_id、PDF页、印刷页、标题/表名、原文、期间、单位` | 只保留“向量”而丢失原文、页码和文件定位 |
| 索引 | SQLite保存资料和片段元数据；本地FAISS保存向量索引；向量模型名称、版本、维度和生成时间进入索引清单 | `embedding_model、embedding_version、index_version、chunk_count、build_time` | 用未记录版本的远程向量服务，或混入不同案例/T0后的资料 |
| 检索 | 先按案例、T0、资料类型和规则做硬过滤；再用规则关键词/字段名与向量相似度混合召回；程序从候选中选出最多6段进入模型 | `retrieval_run_id、query、filter、候选数、排序分、命中evidence_id、入模清单` | 全库无条件检索、任意网页搜索、按模型“感觉”虚构引用 |
| 使用与校验 | R1/R2计算结果与RAG片段共同构成证据包；模型只能引用本次检索命中的ID，程序回填来源与页码 | `run_id、retrieval_run_id、evidence_bundle、提示词/模型版本、校验结果` | 把检索相似度当作事实证明，或跳过Schema、T0、原文和公式校验 |

以R1为例，送入三个角色的资料包只包括：四项已复算数字及公式、对应利润表/资产负债表的来源ID、RAG命中的收入确认政策或应收账款附注中最多两个片段、管理层讨论中最多一个片段、资料缺口列表。若检索不到已定位片段，系统显示“文字资料不足/未检索到可核验支持”，不让模型补写解释。

RAG V1验收使用固定开发问题集：至少覆盖R1收入确认政策、应收账款/账龄、管理层讨论和R2现金流说明四类查询。每个查询至少抽查一次“命中相关片段”和一次“不应命中T0后资料或其他公司资料”的反例；所有展示片段都应能打开原始资料并定位页码。检索排序不作为审计结论，命中失败要留下日志并允许人工从来源台账选择片段。

## 九、数据与资料方案

### 9.1 必需的公开资料白名单

- 交易所、上市公司官网、巨潮资讯等正式披露渠道中的年报、审计报告和公告；
- T0前公开的监管问询、风险提示和更正文件；
- 同行业上市公司年报、招股说明书以及公司公开披露的经营数据；
- 政府部门、行业协会或可说明口径的公开行业统计；
- 国家企业信用信息公示系统等公开官方登记信息，仅在可核验时使用。

新闻、自媒体、论坛和模型记忆不能直接作为正式证据。付费商业数据库不是第一版运行前提。

### 9.2 可选补充资料与续分析窗口

第一版拟在核心链路稳定后，最多支持四类标准化补充资料：合同关键条款摘要、销售明细摘要、发货/验收摘要、期后回款及退货摘要。资料必须获得授权并脱敏，格式为规定Excel模板或少量可读PDF。

**交互路径（拟）：** 审计师按风险卡“待索取资料”清单取得资料后，不另开无关系统，而是在审迹智链内打开**补充资料续分析窗口**，将资料绑定到指定风险卡/风险指标后提交继续分析。窗口最低字段包括：关联 `rule_id`/风险卡 ID、资料类型、文件名或粘贴区、期间、单位、授权确认勾选、脱敏确认勾选、提交人与时间。上传前进行公司、期间、单位、字段完整性和来源授权预检；不通过的资料不得进入分析。通过预检后，程序只将该批资料加入对应卡的资料池并局部重跑；重跑结果仍须硬校验与人工确认，方可更新正式导出内容。

若G6前核心链路未稳定，本项顺延，不影响公开资料预筛和待索取资料清单主交付。演示可用脱敏模拟模板，不接触真实客户机密。

#### 9.2.1 内部资料的三种范围与状态

三种资料放在同一项目资料中心，但使用不同标签、权限和分析状态，不能因“都在一个文件夹”而自动混用：

| 范围 | 它解决什么问题 | 默认是否进入AI分析 |
|---|---|---|
| 待索取资料 | 风险卡告诉项目组下一步需要向客户取得什么 | 否；它是需求清单，不是证据文件 |
| 已取得的请求资料 | 对应清单中已经收到的资料，准备缩小某张风险卡的资料缺口 | 只有绑定风险卡、通过公司/期间/单位/授权/脱敏预检后，才局部进入 |
| 其他内部资料 | 使用者自己已有但系统暂未索取的资料 | 否；先进入“未绑定”资料池，用户确认关联规则和期间后才可进入 |

如果请求资料无法取得，系统保留“未取得/不可评价”状态，并可提示替代性的公开资料或更低敏感度的摘要格式；不得把“用户没有该资料”改写成公司不存在披露或直接给出风险结论。内部资料不会替换公开资料的来源链，而是作为带权限和新 `evidence_id` 的补充范围。

### 9.3 每个案例的最小字段

| 类别 | 主要字段 |
|---|---|
| 财务 | 收入、应收账款、合同资产、存货、营业成本、毛利、经营现金流、信用减值、周转天数 |
| 业务 | 主营产品、销售模式、收入政策、产能产量、客户集中度、结算方式、主要责任人判断 |
| 行业 | 同行收入/毛利率/周转变化、行业景气和价格趋势、常见收入列报方式 |
| 文本披露 | 管理层讨论、重大变化原因、关键审计事项、分部信息及前后年度措辞变化 |
| 元数据 | scene_at_T0、analysis_date、target_period、文件名或网页URL、页面标题、披露/查询/下载日期、PDF页码、印刷页码、文件或存档哈希、T0/T1标签 |

### 9.4 同行对照的工作量上限

每个目标公司默认选择3家、最多5家同行。优先标准为：同一或相近细分行业、主要业务和收入确认模式可比、目标期间一致、会计口径可解释；规模相近只作次级筛选。若产品结构、合并范围、成本范围或披露口径无法合理对齐，则标记“不可比”，不为凑数量强行计算。最终名单和排除理由由B整理、A复核。

### 9.5 案例预检、角色与T0/T1隔离

当前唯一开发样例为标准股份 DEV_T0；它用于网页与后端调试，字段/来源仍待团队专业复核。第二案例尚未选定、未冻结。候选案例先只检查正式来源、公开日期、连续期间、必要字段和PDF可读性，不读取T1内容。随后按用途分流：

| 案例角色 | 冻结前允许的检查 | 使用限制 |
|---|---|---|
| 开发/演示案例 | 可在DEV_T0上运行B0粗扫，优先确认至少1条可解释的R1/R2候选信号；建议再有1—2条辅助信号 | 因已按触发结果选择和调试，只能用于开发复现与演示，不能再称有限留出 |
| 有限留出案例 | 只检查来源、日期、字段和可读性，不看B0触发结果，不运行模型 | 首次模型运行前封存；一旦用于规则、提示词或界面调试，立即降级为开发案例 |

B0预检解决“演示案例完全不触发”的工程风险，但不能被包装成无偏案例选择。若团队没有真正未暴露的案例，须明确报告“无有限留出案例”，不作独立泛化评价。

每个案例须冻结scene_at_T0、analysis_date和target_period，只使用analysis_date前已公开资料。T0与T1分目录保存；T1按监管关注、公司回复、更正和最终监管结论分类，问询或回复不视为事实认定。全部预登记T0运行、输入和日志锁定且获人工授权后才可解锁T1。

两个历史案例仍属目的抽样，只能验证规则、证据约束和端到端工程可行性，不能支持普适舞弊识别准确率或“无风险”保证。

以下是目标信息架构，不以做满页面数量代替跑通链路。当前根目录主网页已有“项目框架、年报资料、R1风险卡、候选指标”四个工作台Tab：候选指标可记录范围，当前只有R1可执行；其余页面与正式导出均未实现。

4. **资料中心、资料缺口与待索取资料：**把未解决问题转成进一步了解或计划阶段核查清单；资料中心分为“公开资料”“待索取清单”“补充资料续分析”“其他内部资料”四个范围，未绑定的其他资料不自动进入分析；每条缺口可跳转到续分析窗口并预填关联风险卡；
5. **人工确认与报告：**人工确认后才允许导出预审风险备忘录；导出范围默认等于用户最终勾选且通过硬校验的指标集合，并显示 `analysis_run` 版本、资料范围和新旧版本差异。

## 十一、技术方案与Vibe Coding实施

以下以目标架构为主，并标注当前实现边界。根目录 `index.html` 是当前主展示网页；截至 2026-07-23，`backend/` 已有 FastAPI入口、`/api/health`、`/api/runs`、运行记录读取和人工复核保存接口。它能对 DEV_T0 的 R1/R2当前工程版做确定性计算并返回对应来源定位；已完成自动化与浏览器联调。后端已有真实三Agent调用代码、JSON/证据ID/禁用词校验和失败关闭，但未配置有效Key时只返回 `config_missing`，尚无三Agent成功记录。PDF自动解析、RAG、官方实时检索、续分析和正式导出仍未实现或验收。

### 11.1 技术结构

- **主展示前端：**保留根目录 `index.html` 和 `assets/` 的视觉与交互；由FastAPI静态托管。后续网页改动继续以该文件为主，不另起Streamlit展示页或第二套前端。
- **本地后端：**Python 3.10+、FastAPI、Pydantic、Uvicorn、pandas、PyMuPDF/pdfplumber、SQLite和FAISS。后端处理PDF页级文本、字段台账、规则计算、RAG索引与检索、模型调用、Schema校验、缓存、日志和导出；浏览器不保存API Key。
- **模型适配层：**只由后端读取 `.env` 中的 `DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、`DEEPSEEK_MODEL`；前端只请求本机 `/api/*`。默认开发路线是DeepSeek官方兼容接口；W2启动时调用官方模型列表确认可用模型ID后，写入配置和运行日志。若当时可用，优先以官方列表中的轻量聊天模型（当前文档列有 `deepseek-v4-flash`）跑开发链路；模型ID不是口头约定，必须随每次运行保存。
- **公开资料入口：**官方披露检索适配器＋本地文件/缓存回放双模式；检索候选必须经过白名单、T0过滤和用户确认，失败时转人工结构化录入。
- **RAG检索层（G5通过后启动、团队终版必做）：**资料预检通过后，SQLite保存页级/片段级元数据，FAISS保存同一片段的本地向量索引；检索采用“案例与T0硬过滤＋规则关键词/字段名＋向量相似度”的混合方式。向量模型可在G5后从可本地运行的中文嵌入模型中选定，但模型名称、版本、维度和索引版本必须冻结并写入检索日志；不把通用网络搜索或模型记忆接成知识库。
- **规则与校验：**规则卡使用独立JSON/YAML和版本状态；输出依次经过Schema、证据ID、日期、原文、公式、字段和禁用词校验；每次运行保存选中指标、参数、数据快照和报告版本，不静默覆盖历史结果。
- **开发方式：**队长使用Trae/Codex等协助编码，队员提供规则、数据和验收标准；代码、提示词、规则和测试样例共同受版本控制。
- **演示保障：**固定案例、经核验缓存、本地SQLite、模型失败状态和备用录屏；缓存与实时结果必须显式区分。

### 11.2 后端接口与网页接入顺序

前端不直接调用任何模型供应商。根目录网页在本地服务启动后调用下列最小接口；接口未完成时，页面显示明确的“未接入/不可用”状态，不伪造分析结果。

| 接口 | 输入 | 后端做什么 | 页面拿到什么 |
|---|---|---|---|
| `GET /api/health` | 无 | 检查服务、数据库、模型配置是否可用；不泄露密钥 | `ready / config_missing / provider_unreachable` |
| `POST /api/sources/prepare` | 已确认的本地PDF或结构化录入 | 建页级文本、来源台账、字段状态和 `evidence_id`；W7同时切片并生成/更新RAG索引；不让模型补数字或页码 | 资料预检清单、缺口、索引状态和可进入计算的字段 |
| `POST /api/rag/retrieve` | `case_id、T0、rule_id、source_snapshot_id、query` | 按固定过滤与混合检索返回已登记片段；记录本次检索，不能访问未预检资料 | `retrieval_run_id、命中片段、来源/页码、未命中状态` |
| `POST /api/runs` | `case_id、current_year、scene、rule_ids、r2_min_gap` | 程序计算R1/R2；按规则构建已登记来源证据包；对已触发规则串行调用三个角色；执行JSON、证据ID与禁用词校验；保存本地运行记录 | `run_id、状态、规则结果、来源、Agent步骤、模型状态` |
| `GET /api/runs/{run_id}` | `run_id` | 读取本地运行记录、角色JSON、校验状态和人工状态 | 风险卡详情及可回看记录 |
| `POST /api/runs/{run_id}/review` | 人工状态与说明 | 保存人工确认/退回，不改变原始模型输出 | 最新人工状态与可导出标记 |

已完成的最小路径为 `health → runs → review`：网页按本次勾选向本地FastAPI发送R1/R2请求，后端完成确定性计算、来源校验和本地运行记录保存。若规则触发且配置有效Key，才进入完整三角色链；无Key、网络失败或JSON越界时停止AI草稿链并返回真实状态。G5通过后再把 `sources/prepare → rag/retrieve → runs` 接成可回放的RAG链。这样可以先证明网页真的连到后端，不必等所有上传、检索和导出功能完成。

### 11.3 模型选择、提示词和预算预估

当前模型边界是“代码可调用、状态如实返回”，不以手写答案冒充已调通。真实的后端模型调用测试使用 `.env` 中配置的官方API Key：从已登记的规则证据包得到符合 `agent_output_v1` 的JSON，并保存模型ID、提示词版本、输入/输出token、输入哈希、响应哈希和耗时。若团队没有可用Key，后端只能返回 `config_missing`；不得把固定链代码写成三Agent已成功运行。

开发阶段的默认参数为：`temperature=0.1`；质疑/反证/复核最大输出为700/700/350 token；角色提示词使用附录E版本化保存。W3最多比较2个候选模型，比较的不是“文采”，而是首轮Schema通过率、证据ID错误数、禁用词命中、平均耗时和实测token。W4选择一个工程主模型；正式评估使用的模型、版本、参数和预算仍须在Research Contract中冻结，后续变更须登记并重跑相关回归。

预算不等到正式评估周才估算。估算式为：

> **预计费用 = 各类运行次数 × 每次角色调用数 × 实测平均输入/输出token × 对应单价 × 1.3缓冲系数。**

B0为确定性程序，原则上不消耗模型token；B1—B3、消融和去标识化对照分别登记调用数。W3先形成数量级估算，W8再按冻结配置给出上限；预算或速率上限不满足时，优先减少重复性附加对照，不削弱证据硬门槛。

按“2案例、B1—B3各5次”粗算，主比较约30个模型工作流；财务单维消融和去标识化若各增加10个工作流，正式部分约50个模型工作流（未含开发、角色内多次调用和失败重试）。W3须用真实DEV样例测得单工作流token后再换算费用，并在预计总额上留30%缓冲；该数量级估算不是已冻结预算。

### 11.4 Vibe Coding不是“只让AI写代码”

团队只对影响规则、数据口径、模型/提示词版本、关键代码或验收结果的变更保留简要记录，不逐条保存无关AI对话。记录至少包含日期、变更项、输入/版本、人工修改、验证结果和未解决问题。专业规则、数据口径和验收结果须由人确认，不能把模型输出直接当作完成品。

### 11.5 演示稳定与三级降级

演示拟按“实时运行 → 经核验缓存 → 同版本备用录屏”三级降级。缓存必须来自冻结输入的一次真实成功运行，并保存模型、提示词、规则版本、输入哈希、运行时间和人工复核状态；界面始终醒目标注“实时”或“缓存回放”，缓存不得冒充本次实时调用，也不得计入正式实验结果。核心公开资料、结构化数据和已核验缓存保存在本地SQLite或等效本地存储中，断网时仍可展示既有核验链路。备用录屏与正式材料的时长、格式以主办方已核验要求为准，不在未核验前写入额外时长承诺。

## 十二、效果评估方案

以下均为拟定评估方案，当前没有实验结果。案例、T0、baseline、模型、提示词、规则版本、指标和预算将在正式实验前通过简化Research Contract冻结；任一关键项未冻结或未获人工确认，不启动B0—B3、消融或T1对照。

### 12.1 四组基线

| 组别 | 方法 | 目的 |
|---|---|---|
| B0 | 固定财务阈值规则 | 检验简单比率能做到什么 |
| B1 | 通用大模型直接阅读材料 | 检验无专业流程时的引用和稳定性问题 |
| B2 | 专业规则+结构化输出，但无反证和硬门槛 | 检验约束机制的增量 |
| B3 | 完整系统：多维交叉验证+反证+硬校验+未接触T1的人工确认 | 评估完整方案，并记录人工环节可能带来的残余偏倚 |

另做一组消融对比：仅使用财务维度，与加入业务、行业和披露维度后的结果比较，重点观察预先定义的T1监管关注事项覆盖和“无可追溯资料依据高优先级线索率”是否改善。

### 12.2 关键指标

下列数值是**拟冻结的工程验收目标，不是当前成绩**；W3开发样例后允许由团队说明理由调整一次，正式实验前必须锁定。

| 指标 | 口径 | 拟定目标/报告方式 |
|---|---|---|
| 引用定位准确率 | 抽查正式风险卡的文件、披露日期、页码、原文和数字是否一致 | 100%；任一关键定位错误即不得导出该卡 |
| 公式复算一致率 | 程序结果与人工Excel复算一致的比例 | 100% |
| 正式卡字段完整率 | 通过Schema、证据ID、日期、原文、公式和禁用词硬校验的比例 | 导出结果100%；同时报告模型首轮有效率，不以重试掩盖问题 |
| 无可追溯资料依据高优先级线索率 | 无可回查依据却进入高优先级的比例 | 0% |
| 回归用例通过率 | 至少20个确定性、缺字段、错页码、错公式及无效JSON样例的预期状态是否正确 | 冻结版本100%；W5起随开发累计，不集中到正式评估周 |
| 5次运行稳定性 | 同一输入5次运行的Top 3集合两两Jaccard相似度（交集/并集）及首要风险类型一致次数 | 平均Jaccard不低于0.67，首要风险类型至少4/5一致；未达标则如实报告并采用缓存演示，不宣称稳定 |
| Top 5事项覆盖 | T0 Top 5与T1后续监管关注的收入事项对照 | 只报告有限案例的实际覆盖数/总数，不设普适准确率目标 |
| 反证与多维增量 | 反证导致的保留/降级/暂缓，以及业务/行业维度相对财务单维新增事项 | 报告逐项变化和来源，不预设必须“更好” |
| 轻量可用性 | 3名非项目成员能否完成“定位来源—理解线索—找到资料缺口”任务 | 至少2人无需口头代操作完成；样本不足或身份不符时只作形成性反馈 |
| 人工效率 | 统一任务下使用与不使用原型的耗时和完整性 | 仅在有合适独立参与者时比较；否则只报告学生试用，不称审计人员效率 |

两个案例不具统计代表性，不能宣传普适“舞弊识别准确率”。正式结论只说明冻结案例、T0资料、规则版本和模型配置范围内的覆盖、引用、稳定和失败情况。系统没有形成正式风险卡时，只能表述为“在本次公开资料和已实现规则范围内，未形成可进入Top 5的待核查事项”，不得写“公司不存在舞弊”或“未发现风险”。

### 12.3 降低并检查模型使用后验信息的风险

正式实验前将物理隔离T1后验材料，记录每份资料的公开日期和哈希，并保留输入清单、运行日志及模型/提示词版本。去标识化同时服务展示合规和模型记忆敏感性检查：在T1解锁前，对公司全称、简称、证券代码和其他直接标识作一致替换，保留转换表与源页映射但不提供给模型，再比较去标识前后的风险类型、引用覆盖和状态变化。该测试只能降低和检查已知案例记忆泄漏风险，不能单独证明模型完全未利用既有记忆。第一版不对财务数字做任意比例的随意扰动，以免破坏报表勾稽关系。

### 12.4 正式实验准入与停止条件

Research Contract按附录D的轻量模板记录案例角色、时点边界、冻结版本、基线、指标、重复次数、预算和解锁人；只在正式实验前填写。关键项缺失时停止正式评估，不生成效果结论。

四人团队采用“最低可行隔离”：能访问T1的人不得在访问后修改该案例的T0规则、提示词或人工确认结果；优先由未接触T1的成员运行和复核。若无法做到完全盲法，则在冻结T0后再允许访问T1，记录人员、时间和接触内容，并把结果标为存在残余偏倚，不使用“独立盲评”表述。

## 十三、伦理、技术与项目风险控制

下表均为拟实施控制。只有相应测试通过并保留记录后，团队才能对外表述该项控制“已实现”或“已验证”。

| 风险 | 可能后果 | 规避措施 |
|---|---|---|
| 产品又被看成投资者工具 | 用户和价值边界不清 | 只设审计师工作流并按§4.2控制输出 |
| 审计师需要的内部资料过多 | 团队无法兼容全部数据 | 首版目标是在最低公开资料清单通过预检时形成核心输出；内部资料仅在核心链路稳定后按资料依据缺口、授权脱敏和规定模板条件性补充 |
| 业务或行业数据缺失 | 规则无法触发或模型猜测 | 每条规则显示资料可得性；缺失即输出证据缺口，不作推断 |
| AI对公司作负面定性 | 伦理和声誉风险 | 案例脱敏、禁用词、证据硬门槛、人工确认和免责声明 |
| PDF解析或表格抽取不稳定 | 引用、数字或页码错误 | W1先做可读性POC；失败时转人工结构化录入＋交叉复核，仍由程序核对来源和原文，不开发通用解析器拖延主链路 |
| 多智能体输出不稳定 | 演示失败或结论漂移 | 固定一轮结构化流程；JSON Schema、证据ID、原文、公式和禁用词逐层校验；有限重试后显式失败，不静默导出 |
| 实时与缓存结果混淆 | 误导评委或污染实验记录 | 界面标明“实时/缓存回放”；缓存只来自冻结输入的经核验成功运行，保留元数据且不计入本次实时结果或正式实验 |
| T1后验信息泄漏 | 回测失真 | 文件隔离、日期白名单、哈希、角色分离、全部T0运行和日志锁定、人工授权解锁及去标识化敏感性检查 |
| 外部公开口径不一致 | 错误比较 | 保存口径、单位、期间和来源；不可比时不计算或转人工复核 |
| 依赖付费数据 | 现场无法复现 | 官方公开来源构成最小闭环，付费数据只列为未来增强 |
| 8条规则同时工程化 | 多条半成品挤占核心闭环 | 先验收R1、R2；R3—R8按资料可得性逐条接入，未通过只保留为规则卡 |
| 两案例结果被过度外推 | 形成不可靠的准确率或“无风险”宣称 | 明确目的抽样和有限案例边界；只报告实际覆盖、失败与适用条件，不宣传泛化能力 |
| 按B0触发结果选案例造成选择偏差 | 演示案例被误称为留出评价 | 允许用于开发/演示，但立即标记DEV_T0并禁止再称有限留出 |
| 模型调用预算或速率不足 | 正式运行中断 | W3依据实测token估算并留30%缓冲；正式实验前冻结上限，必要时削减附加对照 |
| 项目范围继续扩大 | 无法完成可靠原型 | 新功能必须直接服务收入风险、两周内完成且有验收指标，否则延期；补充资料续分析窗口与额外案例均为条件项，核心链未稳不得抢工期 |
| 用户自选指标被误用为“自由判案” | 勾选/取消被理解成可自定义舞弊结论 | 指标仅映射已实现规则；界面固定提示“自选只决定分析范围，不改变证据门槛与人工确认” |
| 补充资料窗口变成开放聊天 | 模型自由发挥、编造页码或结论 | 窗口只接受模板化字段+关联风险卡；禁止无绑定闲聊；重跑结果仍过硬校验 |

正式页面与对外表述统一遵守§1.3；T1监管结论只能在T0日志锁定并获授权后于独立评估区呈现，不得反写为T0系统结论。

## 十四、四人团队任务分工

分工只要求交付当前阶段门直接需要的成果，不设置固定周报、每周录屏、每周新增规则数量或重复管理文件。

### 14.1 队长：工作流与系统整合

负责Web原型、确定性计算、AI固定流程、证据硬门槛、版本/密钥/缓存和阶段集成；在G5通过后实现RAG的入库、切片、SQLite/FAISS索引、混合检索、检索日志和页面回查；实现**风险指标勾选状态机**与（条件项）**补充资料续分析窗口**的上传预检、关联绑定和局部重跑。每周期只需形成当前阶段可运行版本或可复现失败；核心链路未通过时不扩功能。

### 14.2 队员A：审计逻辑与专业规则

负责销售与收款循环、R1/R2优先规则卡、正常解释、资料缺口、候选认定和建议程序，并复核系统措辞与数字；为RAG提供每条规则的检索问题、关键词、同义词、排除词和“命中后仍需人工判断”的说明；为每个已实现规则提供**界面用指标名称、一句话释义、默认是否建议勾选**，以及补充资料进入后对风险假设/正常解释的更新口径。R3—R8按阶段需要修订，不为满足数量强行新增。

### 14.3 队员B：公开数据、同行与评估

### 附录E：Agent Prompt与输入示例（开发第一版）

提示词是代码的一部分，而不是临时在网页聊天框里手改的文案。W3起应将其与规则、Schema一起版本化保存；每次 `analysis_run` 记录 `prompt_version`、模型ID、参数、输入哈希和输出哈希。提示词只要求模型给出可核验的简短理由，不要求或保存模型的详细思维链。

#### E.1 质疑Agent的完整模板

**System Prompt（`challenge_v1`）：**

```text
你是“审迹智链”的质疑Agent，服务于会计师事务所的承接、续聘复核或审计计划阶段。

你的任务：只根据输入中的规则计算结果和 evidence_bundle，提出需要进一步了解的收入或销售与收款循环线索。你不是审计意见系统，不能认定舞弊、重大错报或违法，也不能给投资建议。

必须遵守：
1. 不使用输入之外的公司知识、网页搜索结果或常识补全事实；不能编造数字、文件、页码、原文或 evidence_id。
2. 每条 claim 必须绑定至少一个输入中存在的 evidence_id；无法绑定时不要输出该 claim。
3. 只可使用“待进一步了解”“需要解释”“资料不足”等审计计划阶段措辞；不得使用“舞弊”“造假”“确认存在重大错报”等定性。
4. 不得改算或改写程序给出的字段、单位、公式和触发结果；若资料不足，写入 data_gaps 或 requested_materials。
5. 仅输出一份符合 agent_output_v1 的 JSON；不要 Markdown、前后说明或额外字段。
6. role 必须为 challenge，rule_id 和 run_id 必须原样回填，status 必须为 candidate。
```

#### E.2 反证与语义复核的固定差异

三角色共用E.1中的禁止项、JSON约束、证据ID约束和输出上限；程序只替换角色专属指令和可见输入，避免三个Agent各自“自由发挥”。

| 角色与提示词版本 | 程序额外传入 | 角色专属任务 | 允许状态 |
|---|---|---|---|
| `counter_v1` 反证Agent | `challenge.json`、同一份 `evidence_bundle`、允许的正常解释词表 | 针对每个质疑，寻找输入中能够支持或削弱它的材料；没有材料时明确“未检索到可核验支持”，并列出仍缺资料 | `candidate` 或 `defer` |
| `review_v1` 语义复核Agent | `challenge.json`、`counter.json`、同一份 `evidence_bundle` | 检查每个措辞是否超出证据、是否遗漏反证或资料缺口；只建议保留、降级或暂缓 | `retain`、`downgrade` 或 `defer` |

反证Agent不能为了平衡而强行给出正常解释；语义复核Agent不能新增事实、绕过硬校验或把“建议保留”变成人工确认。程序在把结果送给下一角色前，再次校验JSON和 `evidence_id`；未通过即终止该次AI链并显示失败状态。

#### E.3 提示词、模型与输出的最小留档

每个真实或缓存运行至少保存：`run_id`、输入资料哈希、规则版本、`prompt_version`、模型ID、温度、token上限、每角色输入/输出token、耗时、重试次数、原始响应哈希、解析结果和人工状态。前端仅显示适合审阅的摘要；原始模型响应不得由用户浏览器伪造或覆盖。

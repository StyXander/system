## 1. 总评（判决）

### 1.1 一句话判决

| 对象 | 判决 |
|---|---|
| **`index.html`** | 完成度较高的**竞赛方案展示页** + 诚实的 **R1 DEV 工作台**；远不是完整 AuditTrace 系统。 |
| **计划书 V2.4.2** | 专业边界与工程合同意识强，但**范围过满、状态滞后、与页面/代码三条线未锁死**；再叠加需求会直接伤害可演示性与答辩可信度。 |
| **下一步** | 停止扩写愿景；用计划书登记**已实现事实**；用 2–3 周把「R1 + 证据闸门 + 三 Agent 结构化 + 失败样例」做成**一条可回放主链**。主链不过，RAG / 实时检索 / 八规则一律后置。 |

### 1.2 核心矛盾

计划书写得像一份可交付的“审计智能系统产品合同”，网页却只证明了：

1. 定位、边界、五项创新与流程的**方案叙事**；  
2. 标准股份开发样例上 **R1 四字段确定性计算 + 来源回指 + 可选后端握手**。

若按当前计划书去演示，评委最容易追问：

> 「流程九步、三个 Agent、RAG、指标库、续分析都在——你现在能**真跑通**哪几步？」

当前诚实答案只能是：**确定性 R1 计算 + 来源字段回指 + W2 级后端握手雏形**；其余多为文案与示意。

## 2. 对照事实：主网页实际交付了什么

### 2.1 已经做对、应保留的表述与能力

1. **用户与场景锁定正确**  
   面向会计师事务所审计项目组；业务承接、续聘复核、审计计划；主题为收入确认重大错报风险预筛查；循环为销售与收款。

2. **伦理与输出边界写清楚**  
   不做舞弊认定、不出审计意见、不给投资建议、不替代人工判断；目标输出为预审风险备忘录、最多 5 项待核查事项、待索取资料清单。

3. **演示诚实性较好**  
   导航标注「方案 + DEV 演示」；工作台与状态行写明：R2、公开检索、指标库、RAG、补充资料续分析仍未接入；页脚指向 V2.4.2，并区分开发样例与「拟/计划」。

4. **R1 工程最小闭环雏形存在**  
   - 案例：西安标准工业股份有限公司（标准股份）开发样例；  
   - 期间：2025/2024、2024/2023、2023/2022；  
   - 字段：本年/上年营业收入、本年/上年应收账款；  
   - 约束：`evidence_id`、来源文件、披露日、PDF/印刷页、定位；披露日晚于 T0 或字段不全则不生成候选卡；  
   - 计算：程序计算收入增速、应收增速与差额；单位切换只改展示；  
   - 后端：可请求 `/api/health`、`/api/runs`；无后端时保留本地预览，不把预览冒充后端运行；模型最多做连通检查，不参与 R1 方向结论。

以上说明团队理解竞赛中的「可信表述」，优于伪造 Agent 输出。

### 2.2 页面在“卖”、但尚未交付的内容

| 页面叙事 | 在计划书中的位置 | 当前事实 |
|---|---|---|
| 五项核心创新（含反证、T0/T1） | §7 创新一至五 | 文案卡片；工作台无反证链、无 T1 区 |
| 交叉验证矩阵 | §7.1 / 评分点 | **写死的 R1 一行示意**，非运行结果 |
| 9 步流水线（质疑→反证→复核→硬校验→导出） | §8 主流程 | 工作台仅 **3 个 Tab**；无三 Agent I/O、无正式导出 |
| 三个 AI 角色 | Multi-Agent 卖点 | **职责说明卡**；无结构化 `challenge/counter/review` |
| 预审风险备忘录 / Top 5 | 目标输出 | 未见可导出正式报告 |
| 实时检索 / RAG / 指标库 / 续分析 | P0–P1 目标 | 页面已写「仍未接入」 |

**修改意见结论：**  
主网页应继续作为**唯一展示入口**，但计划书不得把方案区视觉完成度写成系统完成度；凡未接后端、未留运行日志的步骤，在计划书与页面统一标为「设计目标 / 示意」。

## 3. 主要问题（按严重程度）

### 问题 A：状态落笔滞后于工作区现实（必须改）

**现状：**  
V2.4.2 页眉与 §1.1 仍大量沿用「截至 2026-07-17 尚无经验证正式原型……」「后端、真实模型调用……尚未实现或验收」一类表述。

**对照事实：**  
根目录已有 `index.html` 工作台、`backend/`（至少 `health` / `runs`）、`README_RUN.md` 及第二周集成材料。后端仍属 W2 握手级，**不等于**完整系统，但也不等于「尚无原型」。

**风险：**  
老师/评委无法判断哪一份是真源；执行周次与状态表失真。

**修改要求：**

1. 重写页眉「当前状态」与 §1.1，按三层写清：  
   - **已存在开发物：** 根目录展示页 + R1 DEV 工作台 + W2 级 FastAPI 握手；  
   - **已技术联调但未专业定稿：** 标准股份四字段与来源编号（待 A/B 人工复核签字）；  
   - **未实现/未验收：** 三 Agent 固定链、R2、RAG、官方实时检索、指标库、续分析、正式案例与 B0–B3。  
2. §17 人工闸门表同步更新日期与状态，删除与 `README_RUN.md` 冲突的句子。  
3. 约定：每出现可运行物，**同一天**更新计划书状态段；禁止用旧日期句覆盖新事实。

---

### 问题 B：范围“合同化”过度，P1 仍过载（必须改）

**现状：**  
V2.4 至 V2.4.2 连续叠加：官方检索双模式、资料中心分层、指标库与分析版本化、三 Agent + Schema + 硬校验、**RAG V1 必做**、R2、第二案例、B0–B3、回归用例等。

**对照事实：**  
真实进度停在 R1 四字段与来源闸门；RAG / 检索 / 八规则均未落地。

**风险：**  
口头强调「一条完整链路优于多条半成品」，执行清单却同时购买多条战线；文档制造虚假安全感。

**修改要求：**

1. **重写 §5.7 优先级表**，9 月「必须交付」收缩为：  
   - **P0（不可商量）：** 1 个 DEV 案例 × R1（含明确口径）× 来源/公式闸门 × 三 Agent 结构化链 × 硬校验失败样例 × 人工确认 × 可启动 README；  
   - **P1（可提交加分）：** R2 或同等第二条规则、指标勾选、交叉验证矩阵读运行结果、待索取清单与一页备忘录导出、缓存/失败三种真实状态；  
   - **P2（条件项）：** RAG V1、官方实时检索适配器、补充资料续分析、完整 B0–B3、第二案例留出评估。  
2. **将 RAG 从「必做 / W7 必须完成」改为「主链 G5 通过后的条件必做」**：  
   - 未过 G5：材料写「未完成」，不算项目失败；  
   - 过 G5 后优先做「可回放检索 + evidence_id」，不做向量军备竞赛。  
3. §1.5「本轮产品目标确认」保留产品愿景，但每条增加一列：**当前阶段是否阻塞主链**；阻塞项不得写入「9 月最低完成定义」。

### 问题 C：计划书 R1 与网页 R1 不是同一条规则（必须改）

| 维度 | 计划书 §6.2 R1 | 主网页 / 后端现状 |
|---|---|---|
| 核心逻辑 | 应收增速持续快于收入，且周转天数上升；或合同资产/收入占比上升等 | 仅：应收增速 **>** 收入增速（方向触发） |
| 字段 | 三表、附注、信用政策、合同资产等 | 仅 4 个金额字段 |
| 业务节点 | 销售与收款映射 | 固定文案，无节点级数据下钻 |
| 正常解释 / 反证 | 强制检索与记录 | 模板句，非 Agent 输出 |

**风险：**  
专业主张被砍成单指标比较，却仍用「多维交叉验证」叙事；评委按计划书追问即可击穿。

**修改要求（二选一，必须写死）：**

- **方案 A（推荐，短期）：** 在 §6.2 与规则卡中新增 **R1-lite（当前已实现）** 条目：仅增速背离方向规则；完整 R1 标为「待字段与专业复核」。页面与验收一律称 R1-lite 或「R1 当前工程版」。  
- **方案 B：** 两周内补齐至少一项第二信号（如应收周转天数，字段可得则做），再允许继续使用完整 R1 表述。

**禁止：** 计划书写完整 R1、代码跑简化 R1、对外不声明差异。

### 问题 D：演示脚本与可运行物严重错位（必须改）

**现状：**  
§16 五分钟演示要求包含：实时/缓存状态、跨维矛盾、三 Agent 实跑、硬门槛拦截、指标勾选、T1 对照、导出备忘录等。

**对照事实：**  
主网页可稳妥演示的是：边界与定位、载入标准股份样例、年度切换、R1 计算与候选/不形成候选、来源表、本机人工复核入口。

**修改要求：**

1. 将 §16 拆成两版：  
   - **当前可演示版（≤3 分钟）：** 边界 → 样例 → R1 计算与来源 →（若有）失败闸门 → 待索取资料文案；  
   - **目标演示版（5 分钟）：** 仅当对应功能通过阶段门后启用。  
2. 未实现步骤不得写进「现场默认演示路径」。  
3. 创新区矩阵、9 步时间线在材料中统一标注「产品化示意」，演示话术优先指向工作台。

### 问题 E：Multi-Agent 目前主要是章节结构，不是可验证系统（应改）

**现状：**  
§8.4–8.5、附录 E 对 Agent 合同写得很细；页面三角色为静态说明；后端模型调用仅为连通检查。

**修改要求：**

1. 在 §11 / §15 明确 **W3 唯一目标**：R1（或 R1-lite）上质疑—反证—语义复核固定链，留下 3 份 JSON、同一 `evidence_bundle`、至少 1 个校验失败可复现样例。  
2. 未达上述标准前，竞赛材料不得写「已实现多智能体工作流」，只可写「角色分工已设计 / 待接入」。  
3. 不要优先做 Agent 聊天式 UI；优先做可回看日志与失败关闭。

### 问题 F：案例与评估文风超前于决策（应改）

**现状：**  
计划书已写 2 案例、T0/T1、开发/留出角色、B0–B3 与多项指标目标；正式案例与 Research Contract 均未冻结。工作台 DEV 使用标准股份是合理的。

**风险：**  
为演示好看挑触发案例导致选择偏差；或经典后验名企被质疑“剧透式覆盖率”。

**修改要求：**

1. §5.1 / §9.5 / §12 增加醒目框：  
   > 评估章节在案例、T0、模型、规则版本未冻结前，**只定义方法，不承诺效果结论。**  
2. 明确当前唯一开发案例角色 = DEV_T0（标准股份）；第二案例「未选定 / 未冻结」。  
3. B0–B3 保留为正式实验前方案；删除任何接近“将证明 B3 优于……”的口吻，改为“拟比较并如实报告”。  
4. 经典监管案例若进入候选，必须单独论证 T0 可公开资料与后验隔离，不得默认主演示。

### 问题 G：计划书内部优先级互相打架（应改）

同一文档同时存在：

- §5.4 最小闭环优先（正确）；  
- §5.6 48 小时快速 MVP；  
- §5.7 9 月主链；  
- RAG / 检索 / 指标库 / 续分析等多条“必备/必做”。

**修改要求：**

1. 在 §5 开头增加「冲突时的裁决序」：  
   > **§5.4 最小闭环 > P0 主链 > P1 可提交演示 > P2 条件项 > 任何新增产品想法。**  
2. 48 小时 MVP 仅作为内部探路，**不得**写入对外“已完成竞赛级版本”表述。  
3. 新功能入表必须回答：是否直接服务收入预筛主链、两周内可否验收、失败时能否整项延期且不破坏主链。

## 4. 计划书应保留的优点（修订时勿删）

1. 用户不是投资者，场景限定承接 / 续聘 / 计划。  
2. 明确不做舞弊认定、审计意见、投资建议；输出停在线索、缺口、待索取资料。  
3. 证据硬门槛、失败关闭、实时与缓存分离的方向正确，且网页工作台已开始落地。  
4. R1/R2 优先、R3–R8 不假装已实现的原则正确（须与指标库/完整产品图的张力一并改写）。  
5. Schema、Prompt、阶段门、Research Contract 模板体现可复核工程意识，应保留为**开发合同**，但状态必须标「拟执行 / 未验收」。

## 11. 结语

V2.4.2 的价值在于把边界、证据门槛和失败关闭写成了可执行合同；`index.html` 的价值在于用诚实的 DEV 工作台证明团队开始落地，而不是只停留在概念。  

当前最大风险不是“写得不够多”，而是**写得比跑得多**。修改计划书的第一目标应是：

> **让老师、队员和评委看到同一份真相：什么已经能点开，什么仍是设计，什么被主动推迟。**

主链未通之前，任何新增“必做”都是在透支答辩可信度。

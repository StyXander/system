# 审迹智链 V3 立项前批判性复盘与修订说明

> **评审对象：** V2.4.4 详细项目计划书、根目录网页与本地后端现状、`08_计划书批判性评审与修改建议_2026-07-23.md`  
> **评审日期：** 2026 年 7 月 24 日  
> **用途：** 供团队确定 V3 的取舍；不是对项目效果的评定，也不构成审计结论。

## 1. 总体判断

项目的方向没有问题：把范围收在审计承接、续聘和计划阶段的收入风险预筛查，比“万能财务分析系统”更有专业辨识度；“数字、来源、模型结论分开处理”的设计，也比让模型直接下判断更适合审计场景。

真正的问题不是“规划不够多”，而是**当前材料把三种文档混在了一起**：评委看的竞赛方案书、团队的工程执行底稿、未来产品的功能清单。结果是项目的价值、创新和可行性被大量免责声明、远期功能和阶段门淹没。V3 的首要目标，是让评委在前两页就看明白：谁在什么场景下用它、它输出什么、为什么可信、现在已经走到哪里。

## 2. 评委最可能提出的质询

| 维度 | 现有风险 | V3 的处理决定 |
|---|---|---|
| 项目定位 | 资料中曾出现事务所与投行/买方两种定位，容易被问“到底服务谁”。 | 统一为会计师事务所审计项目组；投行/投资研究不再作为目标用户或输出场景。 |
| 专业依据 | R1—R8有合理的审计直觉，但部分规则缺少与认定、收入准则、后续程序的显性连接。 | 增加“准则—认定—线索—资料/程序”矩阵；不把准则直接包装为公式阈值。 |
| 技术创新 | 三Agent、Schema、证据ID的思路已写清，但 RAG 仍停留在设计；评委可能认为“多智能体只是概念图”。 | RAG V1 设为初赛前必须验收项；固定链、真实运行留痕和失败关闭并列为核心验收项。 |
| 现有原型 | R1/R2已能计算，但R2在现金流由正转负、上年基数很小时显示出两千多个百分点，容易损害可信度。 | 增加R2不可比保护：符号翻转、上年基数过小或为零时禁用同比增速和“百分点差”，改报金额变动、现金流/收入及“需人工解释”。 |
| 落地节奏 | 原计划把方案书、视频放在后期；而竞赛先盲审 PDF 与视频。 | 方案书、视频、原型从 W3 起并行；8 月底前完成初赛包，而非等到原型“全做完”。 |
| 效果评价 | B0—B3设计严谨，但开发样例未冻结、案例数量少，不能支持“优于基线”或“识别准确率”之类结论。 | 初赛先报告确定性过程指标；正式比较只在 Research Contract、案例和T0/T1冻结后开展。 |
| 交付物口径 | `08` 中把初赛和后续原型评审的表述过度二分。 | 按竞赛手册表6：9月1—25日提交PDF和视频盲审；9月25—30日对进入该阶段的团队评审代码、演示视频和技术报告。因此材料与原型都不能后置。 |
| 团队协作 | 技术工作集中在队长，其他成员的输入不够“可验收”。 | 每一条核心能力都列出A/B/C可交付的规则、来源、测试或表达物；队长只负责集成，不承担所有事实判断。 |

## 3. 对 `08` 建议的取舍

| `08` 建议 | V3 决定 | 原因 |
|---|---|---|
| 方案书与工程底稿分离 | 采纳 | V3 为评委阅读主稿；V2.4.4保留为内部详细底稿。 |
| 把 CAS 1211、CAS 14 写进专业基础 | 采纳 | 增加经核验的准则条款与规则矩阵，强化专业深度。 |
| RAG V1初赛前完成 | 采纳为团队硬目标 | 团队已明确RAG要做；但只有通过页码、来源、T0过滤和反例测试后，才可称“已实现”。 |
| 用 Agent-as-a-Judge 表述语义复核 | 部分采纳 | V3说明其与该范式的关系，但不靠术语冒充技术成果；核心仍是复核范围受证据和程序校验约束。 |
| 不用 LangChain/AutoGen 也要说明 | 采纳 | 固定三步链直接调用更易审计和复现；不为了“用了框架”增加不可控状态。 |
| 初赛只看方案书和视频，因此原型可后置 | 不采纳原表述，改为并行 | 手册还规定后续阶段需代码、演示视频和技术报告；原型必须持续推进，但不能挤掉初赛材料。 |
| 初赛前必须做 B0 与 B3 对比 | 修改采纳 | 可先做一次开发样例的工程对照，但不能把单例结果称为系统优于基线；评价结论须等冻结后形成。 |
| 第二案例立即完成 | 采纳为P1 | 第二案例先完成R1字段、来源和T0可得性检查；不在主链未稳定时一次性铺开R2—R8。 |

## 4. V3 必须守住的四条红线

1. **不把开发样例写成正式案例或实验结果。** 标准股份当前仅为 DEV_T0；来源技术交叉核验不等于专业定稿。
2. **不把模型输出写成审计结论。** 输出只可为待核查线索、正常解释、资料缺口和待索取资料；最终保留与后续程序由人决定。
3. **不把RAG、三Agent、公开检索等目标功能写成已实现。** 每项能力均需要代码、测试和可回查运行记录三者之一以上的对应状态。
4. **不以夸张比率替代审计判断。** R2的正负转换/极小基数必须显示为不可比，而不是“数千个百分点”的风险暗示。

## 5. V3 的验收重点

| 截止节点 | 必须拿到的证据 | 不通过时的处理 |
|---|---|---|

| 2026-08-20 | 初赛方案书、5分钟视频首版、核心回归测试记录 | 砍掉条件功能，保证方案书、视频和主链质量。 |
| 2026-08-31 | 提交级PDF、视频、启动说明与演示录屏冻结 | 只修严重错误，不新增规则或案例。 |

## 6. V3 结论

V3 不再承诺“把八条规则、RAG、检索、内部资料、评估和产品化一次做完”。它承诺一条能讲清楚、能运行、能回查、能被人接手的主线：**公开资料预检 → 规则计算 → 受控检索 → 质疑/反证/复核 → 程序硬校验 → 人工确认 → 待索取资料。**

V3 的强项应是“有约束的智能体审计预筛”，不是功能数量。后续扩展只能在这条主线稳定后进入。

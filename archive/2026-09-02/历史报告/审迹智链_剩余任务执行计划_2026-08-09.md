## 4. 当前明确未完成的主问题

### P1：fresh-web RAG 本地旧索引与远端新快照可能误绑定

这是当前最明确、必须先修的剩余问题。

#### 当前表现

`backend/app/main.py` 当前逻辑仍有两个问题：

1. `GET /api/rag/status` 只要本机公开案例索引显示 `ready`，就直接返回本机状态，未先比较 Supabase 当前 active snapshot。
2. `POST /api/rag/retrieve` 只要本机存在公开案例，就使用本机索引检索；随后却可能把 Supabase 的远端 `rag_snapshot_id` 写入检索日志。

典型复现：

1. web 实例本地保留旧 RAG 索引 A。
2. worker 在 Supabase 发布新快照 B。
3. web 仍从 A 检索，但日志和响应声称证据来自 B。

这会造成证据链误绑定，属于验收阻断。

#### 目标合同

在 Supabase 模式下：

1. Supabase active snapshot 是跨实例权威。
2. 本机索引只有在下列信息全部一致时才可作为计算加速层：
   - `case_scope`
   - `rag_snapshot_id` 或可重复计算出的完整快照摘要
   - `source_fingerprint`
   - `index_version`
   - `chunk_count`
3. 任一项不一致时，必须走 `_remote_rag_retrieve`，不能使用本机旧索引。
4. 检索日志必须记录“实际执行检索的快照 ID”，不能用远端 ID 给本机结果代填。
5. Supabase 状态不可用时要 503 失败关闭，不能静默回退到可能陈旧的本机证据。
6. local 模式仍可直接使用本机索引，不受公网权威逻辑影响。

#### 推荐实现

优先采用一个共享、可重复的 snapshot descriptor：

- 将 RAG 快照摘要计算提取成单一函数，pipeline、adapter 和 web 比较都复用。
- 远端 status 返回：`rag_snapshot_id`、`source_fingerprint`、`index_version`、`chunk_count`、`generation_id`。
- 本机 manifest 同样暴露上述字段。
- 增加 `_local_rag_matches_remote(local_status, remote_status)`，仅全等时走 local。
- `rag_retrieve` 分支先确定 `actual_snapshot_id`，再持久化 retrieval log。

#### 必须新增的测试

1. 本机旧 A、远端新 B：走远端检索，日志绑定 B。
2. 本机与远端完全一致：允许走本机，日志绑定实际相同快照。
3. snapshot ID 相同但 index version 不同：走远端。
4. source fingerprint 不同：走远端。
5. 远端 ready、本机 not built：走远端。
6. 远端查询 503：失败关闭，不返回本机旧结果。
7. local 模式：继续走本机。
8. 租户 A 的 retrieval ID，租户 B 与匿名均不能读取。

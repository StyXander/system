# 审迹智链竞赛 Demo 去登录与全案例直出：详细执行计划

> 日期：2026-08-10
> 文档性质：实施说明与本轮实际执行记录；本地验收已完成，线上部署需以推送后的 Render 版本为准。
> 核心目标：将当前工程从“生产级多租户网站”收敛为“比赛现场可稳定演示的产品思路 Demo”。登录、租户、隐私授权和模型同意不再阻塞演示；50 家内置上市公司案例可直接打开、分析并下载演示报告；补充资料流程继续保留，并能形成追加分析结果。

---

## 一、比赛版最终要呈现的完整故事

现场演示应只保留以下主线：

1. 评委输入公司名称或股票代码。
2. 系统从内置 50 家目录或巨潮资讯公开年报中定位公司。
3. 系统展示公司、股票代码、分析年度和年报来源。
4. 系统直接运行确定性规则、行业专用预筛和 RAG 原文检索。
5. 外部模型可用时生成三角色分析草稿；外部模型暂时不可用时，仍输出确定性演示草稿，不能让页面卡死或没有报告。
6. 系统展示候选风险、证据、数据缺口、原文片段和方法边界。
7. 用户上传一份公开样例补充资料。
8. 系统把补充资料作为独立证据加入原运行，形成“补充前/补充后”的追加分析。
9. 用户直接下载带有“竞赛演示、未经真人专业复核”水印的 Word 报告。

本比赛版不演示以下内容：

- 注册、登录、刷新令牌、退出登录；
- 多租户组织和角色权限；
- 私有 Storage、保密审批、脱敏确认；
- 逐案例外部模型传输同意；
- 独立队列 worker、租约和分布式任务恢复；
- 面向真实公众长期开放所需的生产安全能力。

上述生产能力可以保留在代码中，但比赛部署不得进入这些路径，也不得在界面上出现“请登录”“等待同意”“私有资料不可用”等阻塞信息。

## 二、必须坚持的边界

### 2.1 Demo 模式必须是显式开关

新增并统一使用：

```text
AUDITTRACE_DEMO_MODE=true
AUDITTRACE_PUBLIC_DEMO=true
AUDITTRACE_PERSISTENCE=local
```

所有简化行为只在 `AUDITTRACE_DEMO_MODE=true` 时生效。默认值仍应为关闭，防止后续误把比赛版逻辑当成生产安全方案。

### 2.2 不建议删除生产认证代码

不要大面积删除 `auth.py`、Supabase schema、RLS 或 worker。正确做法是：

- 比赛部署只启动单个 Web 服务；
- 前端完全隐藏登录和同意控件；
- 后端 Demo 分支使用本地匿名演示身份；
- 生产分支继续保留原合同和测试。

这样既降低比赛演示复杂度，也避免以后需要生产化时重新开发全部安全能力。

### 2.3 不能把“演示”包装成真实审计结论

所有页面、JSON 和报告必须保留以下含义：

```text
竞赛演示结果，仅用于展示审计计划阶段的产品思路；未经真人专业复核，不构成审计结论或审计意见。
```

如果外部模型不可用而使用确定性模板生成草稿，必须标记为“演示模拟生成”，不得声称真实模型调用成功。

## 五、详细实施步骤

## 阶段 A：建立统一 Demo 模式

### A-1 后端模式函数

目标文件：`backend/app/main.py`

建立唯一判断函数，例如：

```python
def _competition_demo_enabled() -> bool:
    return os.getenv("AUDITTRACE_DEMO_MODE", "").strip().lower() in {"1", "true", "yes", "on"}
```

禁止在不同路由中重复写不同环境变量判断，避免一部分页面认为是 Demo，另一部分仍要求登录。

### A-2 状态接口

目标文件：`backend/app/main.py`

`GET /api/status` 在 Demo 模式增加：

```json
{
  "demo_mode": {
    "enabled": true,
    "login_required": false,
    "supplement_policy": "public_sample_material",
    "boundary": "竞赛演示仅展示产品思路；账号、多租户和生产保密流程未启用。"
  }
}
```

验收：前端只能以该字段判断是否隐藏登录，不得根据 Supabase 是否报错来猜测。

### A-3 部署配置

目标文件：`render.yaml`

比赛版只保留一个 `type: web`：

```yaml
- key: AUDITTRACE_DEMO_MODE
  value: "true"
- key: AUDITTRACE_PUBLIC_DEMO
  value: "true"
- key: AUDITTRACE_PERSISTENCE
  value: local
```

比赛版删除或禁用：

- `type: worker`；
- `SUPABASE_SERVICE_ROLE_KEY`；
- 仅用于生产多租户的 Supabase 环境变量。

保留外部模型配置，但不得把模型密钥写入仓库。

## 阶段 C：修通 50 家案例直接分析

### C-1 统一公开种子案例为运行输入

目标文件：

- `backend/app/seed_catalog.py`
- `backend/app/main.py`
- `backend/cache_seed.materialized.json`

要求：

1. `GET /api/cases` 在 Demo 模式始终返回 50 家公开演示企业。
2. `GET /api/cases/{case_id}` 返回字段、文档、年份和行业规则信息。
3. `POST /api/runs` 找不到本机案例目录时，必须回退到种子案例。
4. 回退只能使用可发布字段，不能泄露本机路径、Storage 路径或整本 PDF。
5. 同一股票代码只能出现一个当前演示案例。

### C-2 修复 `source_file` 假缺失

目标文件：`backend/app/main.py`

重点检查 `_industry_period_sources`。禁止使用下面这种逻辑：

```python
source.setdefault("source_file", document.get("source_file"))
source.setdefault("source_file", document_id)
```

因为键一旦存在且值为 `None`，第二次 `setdefault` 不会回填。

应改成有效值回退：

```python
source["source_file"] = (
    source.get("source_file")
    or document.get("source_file")
    or source.get("document_id")
    or document.get("document_id")
)
```

`file_sha256`、`source_locator`、`document_id`、`unit` 也要使用同类有效值回退，不得把空字符串和 `None` 当成有效来源。

验收：50 家案例运行结果中字符串 `SOURCE_INCOMPLETE` 出现次数必须为 0。

### C-3 年度选择

案例可运行年度按以下优先级选择：

1. `available_years`；
2. `available_report_years`；
3. `documents[].report_year`。

对行业字段不足的公司，不得因为 `available_years=[]` 就使公司完全不可运行；应使用最新报告年度输出 `DATA_GAP` 报告。

### C-4 对 7 家诚实输出数据缺口

当前预期可能进入 `DATA_GAP` 的公司：

- 申万宏源 `000166`；
- 中信证券 `600030`；
- 招商证券 `600999`；
- 中国人保 `601319`；
- 华泰证券 `601688`；
- 建设银行 `601939`；
- 中国银行 `601988`。

这些公司不能显示“分析失败”或空白页，而应形成完整的“数据缺口型演示报告”，包含：

- 已获得的三年年报；
- 已执行的行业适配判断；
- 缺失的专用字段；
- 为什么不能计算金额；
- 建议补充的资料；
- 可继续执行的 RAG 证据；
- “未猜测金额”的边界。

## 阶段 D：让 RAG 和模型不再卡住演示

### D-1 50 家种子 RAG 摘要

目标文件：

- `scripts/build_public_catalog_seed.py`
- `backend/app/seed_catalog.py`
- `backend/cache_seed.materialized.json`

构建种子时，每家公司按固定问题保存少量可发布证据摘要：

- `question_id`；
- `document_id`；
- 年度；
- PDF 页码；
- 内容哈希；
- 有长度上限的原文摘要。

不得打包：

- 整本 PDF；
- FAISS 二进制索引；
- 本机绝对路径；
- 私有 Storage 地址。

`/api/rag/status`、`/api/rag/retrieve` 和检索日志接口在没有本机索引时使用这些摘要，页面必须能展示证据，而不是永久显示“未构建”。

### D-2 外部模型可选，不得成为单点失败

目标文件：

- `backend/app/main.py`
- `backend/app/agents.py`

Demo 完整分析按以下顺序：

1. 先完成规则和 RAG；
2. 如果模型配置和调用均成功，展示真实模型草稿；
3. 如果模型未配置、超时、配额不足或不可达，使用确定性演示草稿；
4. 演示草稿只能引用本次 evidence bundle 中的证据 ID；
5. 演示草稿必须标记 `generation_mode=deterministic_demo_fallback`；
6. 页面不得把它显示成“真实模型调用成功”。

确定性演示草稿至少包括：

- 为什么形成候选或为什么未触发；
- 一项正常解释；
- 数据缺口；
- 建议取得的补充资料；
- 证据 ID；
- “未经人工复核”的声明。

## 阶段 E：补充资料和追加报告

### E-1 保留独立证据边界

目标文件：

- `backend/app/supplements.py`
- `backend/app/main.py`

补充资料不能静默覆盖原年报字段。应放入：

```text
evidence_bundle.supplement_evidence
```

每条补充证据至少包含：

- `evidence_id`；
- `supplement_id`；
- 资料类型；
- 截止日期；
- 来源文件或结构化样例；
- 支持状态；
- 是否待人工确认。

### E-2 提供现场可用的样例

前端至少提供一个“一键填入演示样例”，例如：

```json
{
  "aging_summary": {"over_180_days_ratio": 0.21},
  "subsequent_receipts_summary": {"receipt_ratio": 0.63}
}
```

用户也可以上传 CSV、XLSX、DOCX 或 PDF 样例，但第一版比赛演示应优先保证结构化 JSON/CSV 稳定。

### E-3 追加报告结构

目标文件：`backend/app/delivery.py`

报告新增章节：

1. 原始公开年报预筛结果；
2. 本次补充资料；
3. 补充资料证据列表；
4. 补充前建议；
5. 补充后建议；
6. 建议变化原因；
7. 仍然存在的数据缺口；
8. 演示与人工复核边界。

Demo 未人工复核时允许生成 Word，但必须加醒目水印：


## 一、结论与推荐方案

本项目应采用“行业适配闸门 + 50 家预热缓存 + 其他企业实时巨潮流程”的混合架构，而不是把所有上市公司强行套进同一条 R1 规则，也不是每次都重新下载相同年报。

推荐落地方式：

1. 在字段提取前增加行业适配闸门，先判断当前企业、报表体系和所选规则是否匹配；
2. 对约 50 家常用或演示企业预先下载并校验最近 3 年年报，预建结构化字段和 RAG 索引；
3. 用户再次分析这 50 家企业时直接读取已校验快照，只重新执行版本匹配的规则，达到秒级进入结果页；
4. 对数据库外企业继续执行“巨潮搜索—下载—校验—RAG—字段—分析”的现有完整流程，并在成功后自动进入缓存；
5. 本地竞赛版使用 SQLite 保存元数据和结构化结果，PDF 与 FAISS 文件单独保存；线上多用户版再迁移到 PostgreSQL、对象存储和独立任务队列。

这套方案既能让常用企业快速响应，也保留“输入任意新企业”的扩展能力。数据库不是替代巨潮，而是保存已经从巨潮取得并验证过的公开数据快照。

## 二、为什么必须先做行业适配闸门

当前 R1 的核心问题是“应收账款增速是否明显高于营业收入增速”。它适合存在可比营业收入和应收账款、且科目含义相对稳定的非金融企业，但不能自然覆盖所有上市公司。

以下情况不能简单视为“字段没找到”：

- 银行、保险、证券等金融企业使用不同报表结构和风险指标，R1 不应直接运行；
- 房地产、建筑、平台型企业可能需要同时考虑合同资产、应收票据或长期应收款，单一应收账款口径可能不完整；
- 合并报表、母公司报表、境内准则和境外准则可能使用不同科目名称；
- 综合集团可能跨多个行业，不能只依靠公司简称判断；
- 年报确有字段，但提取器不认识单位、附注编号或版式，这是技术适配失败，不是行业不适配。

因此必须把三种状态分开：

1. **规则适用且字段齐全：** 正常计算；
2. **规则原则上适用，但技术提取或口径仍有缺口：** 保留 RAG，显示字段缺口并进入适配/复核；
3. **规则本身不适用：** 不运行 R1，改用该行业规则或只展示行业风险检索结果。

## 三、行业适配闸门设计

### 3.1 闸门位置

目标流程调整为：

```text
输入企业
  ↓
公司与证券代码确认
  ↓
缓存命中检查
  ↓
获取或读取官方年报快照
  ↓
识别报表体系、行业和可用字段
  ↓
行业适配闸门
  ├─ A：当前规则直接适用 → 字段提取 → R1/R2 → 结果
  ├─ B：条件适用 → 专用口径/字段映射 → 降级预筛
  ├─ C：当前规则不适用 → 行业专用规则或 RAG 风险摘要
  └─ D：无法可靠识别 → 明确提示人工选择，不猜行业
```

闸门必须位于规则执行之前，但不阻止年报下载、来源校验和 RAG 建库。这样即使 R1 不适用，用户仍能快速检索公开年报中的风险、会计政策和经营情况。

### 3.2 四级适配结果

| 等级 | 含义 | 系统动作 | 页面表达 |
|---|---|---|---|
| A `direct` | 报表体系和字段与当前规则直接匹配 | 运行 R1/R2 | “行业与规则适配，可直接预筛” |
| B `conditional` | 规则可参考，但需要专用字段映射或口径限制 | 只运行已验证规则，展示限制 | “条件适用，部分指标按专用口径计算” |
| C `not_applicable` | 当前规则不适合该行业 | 跳过 R1，保留 RAG 和行业提示 | “当前规则不适用，不代表企业无法分析” |
| D `unknown` | 行业或报表体系无法可靠确认 | 不执行数值规则，要求选择 | “待确认行业/报表体系” |

### 3.3 第一版行业分组

第一版不要一次性开发几十套规则，先完成稳定分流：

- **普通工商企业：** 制造、零售、能源、交通、信息技术、医药等，默认允许测试 R1/R2；
- **条件适用行业：** 房地产、建筑、平台经济、租赁等，需要登记额外字段或口径限制；
- **金融行业：** 银行、保险、证券、信托，R1 默认不适用，只提供 RAG 与行业专用指标路线图；
- **未知或综合集团：** 不自动猜测，允许用户选择主要报表体系并保存依据。

中国海油属于能源类普通工商企业，R1 原则上适用。本次失败由“人民币百万元”单位表头和附注编号版式未被识别造成，不应被行业闸门拦截。

### 3.4 闸门输入与确定性证据

闸门应按以下顺序取证，不允许只让大模型自由判断：

1. 巨潮公司元数据中的证券代码、市场和行业字段；
2. 年报中的行业分类、主营业务、执行会计准则和财务报表标题；
3. 结构化字段存在性与报表科目名称；
4. 项目维护的行业覆盖表；
5. 只有前四项冲突时，才让 AI 生成“待人工确认建议”，AI 不直接放行规则。

建议闸门输出：

```json
{
  "case_id": "CNINFO_600938_T0_20260326",
  "industry_family": "energy",
  "reporting_profile": "PRC_GAAP_NON_FINANCIAL",
  "fit_level": "direct",
  "allowed_rules": ["R1", "R2"],
  "blocked_rules": [],
  "required_fields": ["revenue", "accounts_receivable"],
  "reason_codes": ["NON_FINANCIAL_STATEMENTS", "AR_AND_REVENUE_DISCLOSED"],
  "confidence": "high",
  "evidence": [
    {"document_id": "...", "pdf_page": 120, "locator": "合并资产负债表"}
  ],
  "gate_version": "industry_gate_v1"
}
```

### 3.5 失败关闭规则

- 行业不适用时跳过规则，不显示“数据不足导致失败”；
- 技术提取失败时显示“年报有字段，但系统未可靠解析”；
- 真正缺报或缺字段时显示“官方公开资料未找到”；
- 任何状态都不得显示“无风险”；
- 行业分类、规则版本或字段映射变化后，旧缓存必须重新评估；
- 页面必须展示闸门版本、理由代码和至少一个可回查证据。

## 四、50 家极速数据库设计

### 4.1 是否可以使用 SQL 数据库

可以，而且很适合当前规模。50 家企业、每家 3 至 5 年年报的元数据和结构化字段量很小，SQLite 足以支撑竞赛本地版。它不需要单独安装数据库服务，便于一键启动和打包。

但不要把所有内容都塞进一个 SQL 文件：

- SQL 保存企业、年报、哈希、字段、证据页码、任务、运行和版本；
- PDF 原件保存在按哈希命名的文件目录或对象存储；
- RAG 原文块元数据可进入 SQLite，FAISS 索引文件单独保存；
- 不建议把几百份 PDF 作为 BLOB 放进 SQLite，否则备份、更新和部署都不方便。

### 4.2 推荐存储结构

```text
backend/runtime/
  catalog.sqlite3
  documents/
    8B/8B8B0577...pdf
  rag_indexes/
    CNINFO_600938_T0_20260326/
  pipelines/
  runs/
```

数据库建议包含以下表：

| 表 | 关键字段 | 作用 |
|---|---|---|
| `companies` | `ticker`、名称、市场、行业、状态 | 企业主数据 |
| `company_aliases` | 别名、历史名称、对应 ticker | 避免同名误判 |
| `report_documents` | 年度、公告日期、官方 URL、SHA-256、页数 | 年报版本和来源证据 |
| `source_snapshots` | 案例、T0、文档集合指纹 | 冻结一次分析使用的资料范围 |
| `financial_facts` | 字段、年度、数值、单位、口径、版本 | 结构化财务数据 |
| `fact_evidence` | evidence ID、PDF 页、原文窗口、文档哈希 | 数字回查链 |
| `industry_profiles` | 行业组、报表体系、适用规则、映射版本 | 行业闸门配置 |
| `industry_gate_results` | 案例、等级、理由、证据、闸门版本 | 每次适配判断 |
| `rag_manifests` | 索引版本、块数、指纹、构建时间 | RAG 缓存状态 |
| `rag_chunks` | 块编号、页码、文本哈希、文档编号 | 原文块索引元数据 |
| `pipeline_tasks` | 状态、步骤、重试、错误 | 自动流程任务 |
| `analysis_runs` | run ID、规则版本、完整性、结果路径 | 分析运行记录 |
| `cache_refresh_jobs` | 企业、原因、计划时间、状态 | 预热和更新任务 |

关键唯一约束：

- 企业：`ticker + market`；
- 年报版本：`ticker + report_year + sha256`；
- 财务事实：`snapshot_id + field_kind + year + statement_scope + basis + extractor_version`；
- RAG：`source_fingerprint + index_version`；
- 分析：保留独立 run ID，不覆盖历史结果。

### 4.3 热路径与冷路径

**热路径：数据库已命中且版本一致**

```text
输入企业 → 命中公司与最新快照 → 校验缓存版本 → 读取字段/RAG → 行业闸门 → 执行规则 → 展示结果
```

无需重新搜索和下载。目标是数秒内打开确定性预筛结果；如果需要调用外部模型，耗时单独显示，不能把模型等待时间算成数据库读取时间。

**冷路径：未命中或缓存过期**

```text
输入企业 → 未命中/过期 → 巨潮搜索下载 → 校验与建库 → 写入数据库 → 行业闸门 → 分析 → 展示结果
```

冷路径成功后，下一次自动变为热路径。

### 4.4 缓存命中不能只看公司名称

只有同时满足下列条件才允许极速复用：

- 证券代码和市场一致；
- 目标年度年报齐全；
- 官方 URL 与文件 SHA-256 未发生替换；
- 来源校验版本仍兼容；
- 字段提取器版本仍兼容；
- 行业闸门版本仍兼容；
- RAG 索引版本和来源指纹一致；
- 规则版本与缓存结果一致。

任一版本变化时，应只重建受影响部分。例如规则版本改变只重跑规则，不重新下载 PDF；切块策略改变只重建 RAG，不重新搜索年报。

### 4.5 50 家企业如何选择

首批 50 家不应只选“容易成功”的制造企业。建议按用途分层：

- 20 家普通工商企业，用于稳定 R1/R2 主链；
- 10 家能源、交通、零售、医药等不同版式企业，用于字段适配；
- 10 家房地产、建筑、平台型企业，用于条件适用闸门；
- 6 家银行、保险、证券企业，用于验证“不适用但 RAG 可用”；
- 4 家综合集团、修订年报或特殊版式企业，用于失败关闭和人工确认。

每家公司至少冻结：证券代码、最近 3 年年报、官方 URL、SHA-256、页数、字段证据、行业闸门结果、RAG 指纹和一次可复现运行记录。

### 4.6 本地与线上部署边界

| 环境 | 推荐方案 | 原因 |
|---|---|---|
| 竞赛本地演示 | SQLite + 本地 PDF/FAISS | 安装简单、可离线复演、50 家规模足够 |
| 单机持久化部署 | SQLite + 持久化磁盘或 PostgreSQL | 避免重启丢缓存 |
| 多用户线上版本 | PostgreSQL + 对象存储 + 任务队列 | 解决并发写入、任务恢复和文件持久化 |

如果部署平台的本地磁盘是临时磁盘，不能只把运行时 SQLite 和 PDF 放在默认目录。竞赛阶段可把“已确认的只读种子库”作为版本化资产，再在启动时复制到可写持久化目录；正式线上版应使用持久数据库和对象存储。

## 七、测试计划

### 7.1 行业闸门测试

- 普通制造和能源企业进入 A；
- 房地产或建筑按配置进入 B；
- 银行、保险、证券进入 C，R1 不执行但 RAG 可检索；
- 行业元数据冲突进入 D，不让 AI 自动放行；
- 行业规则版本变化后旧判断变为 `stale`；
- 每个结果都有理由代码和证据页码。
